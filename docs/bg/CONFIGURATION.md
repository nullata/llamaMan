<a id="running-bare-metal"></a>
## Работа директно на хоста

Полезно за разработка или за хостове (напр. WSL), където пускането на самия мениджър в Docker е неудобно. llama-server продължава да работи в контейнери.

```bash
pip install -r requirements.txt
MODELS_DIR=./models DATA_DIR=./data LOGS_DIR=./logs \
  LLAMAMAN_NODE_NAME=dev python app.py
# or under gunicorn:
MODELS_DIR=./models DATA_DIR=./data LOGS_DIR=./logs \
  LLAMAMAN_NODE_NAME=dev gunicorn -c gunicorn.conf.py app:app
```

Един процес под gunicorn обслужва UI/API на `:5000` и проксито на `:42069` (`python app.py` без gunicorn пуска dev сървъра на Flask само на `:5000`). Контейнер или bare-metal се разпознава автоматично; ако разпознаването някога сгреши за вашата среда, задайте изрично `LLAMAMAN_IN_DOCKER=true` или `false`.

<a id="authentication-detail"></a>
## Подробно за удостоверяването

Два вида идентификационни данни:

- **Сесийни бисквитки** за UI (създават се през `/setup` при първо стартиране)
- **API ключове** за външни клиенти (`Authorization: Bearer llm-xxxxxxxxxx`), управлявани в **API Keys** в UI

Превключвателят **"Require authentication for all endpoints"** (включен по подразбиране) определя дали ендпойнтите, обслужващи модели, изискват bearer токен:

| Превключвател | Ендпойнти за модели (`/api/chat`, `/v1/chat/completions`, портове на инстанциите) | Ендпойнти за управление (`/api/instances` и др.) |
|--------|--------------------------------------------------------------------------|-----------------------------------------------|
| **ON** (по подразбиране) | Изисква се bearer токен | Bearer токен или сесия |
| **OFF** | Отворени | Bearer токен или сесия |

И трите групи портове (5000, 42069, 8000-8020) минават през една и съща кука за удостоверяване.

<a id="gpu-stats"></a>
## Статистика за GPU

VRAM и натоварване по GPU, получени нативно - не е нужен работещ llama-server.

| Производител | Метод | Изискване |
|---|---|---|
| NVIDIA | `nvidia-ml-py` (директно през NVML) | Разкоментирайте `deploy.resources.reservations` в `docker-compose.yml` за възможността `utility` на NVIDIA toolkit |
| AMD | sysfs `/sys/class/drm` | Монтиран том `/sys/class/drm:ro` (включен по подразбиране) |
| Intel Arc | sysfs `/sys/class/drm` | Същото монтиране като при AMD |

Без нативен достъп llamaMan прибягва до изпълнение на `nvidia-smi` / `rocm-smi` в работещ контейнер. Статистиката винаги отразява пълното състояние на GPU-тата на хоста.

<a id="request-recording--stats"></a>
## Записване на заявки и статистика

В **Settings → App Settings → Request recording**: **Off** (по подразбиране) / **Per request** / **Per conversation** (репликите се групират по хеш на съдържанието на системния промпт + първото потребителско съобщение). Всеки запис съдържа телата + полетата на обвивката (модел, ендпойнт, статус, продължителност, брой токени) плюс **точни метрики за всяка реплика** (пропускателна способност, измерена в прозореца на генериране; TTFT). Записите се пазят в `RECORDINGS_DIR` (JSON) или в таблицата `request_log` (MariaDB). **Retention (days)** изчиства на всеки час (`0` = пази завинаги).

Всяка карта на инстанция има бутон **Stats** (брой заявки, средна/пикова пропускателна способност, средни TTFT/латентност, общо токени, период на активност), обобщен от журнала на заявките - затова се запазва и след спиране на инстанцията и показва празно състояние, когато записването е изключено. Връзката **Logging** в заглавната лента отваря табло на цяла страница (обобщаващи плочки, скорошни разговори, детайли по разговор) с избор на период 24h / 7d / 30d / All плюс филтри по модел и по ден върху списъка с разговори.

<a id="storage-backends"></a>
## Бекенди за съхранение

### JSON (по подразбиране)

Без конфигурация. Файлове в `DATA_DIR` (`/data`): `state.json`, `presets.json`, `users.json`, `settings.json`, `api_keys.json`, `request_log/`. Логовете на инстанциите и изтеглянията отиват в `LOGS_DIR` (`/tmp/llama-logs`).

### MariaDB / MySQL

```sql
CREATE DATABASE llamaman CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'llamaman'@'%' IDENTIFIED BY 'yourpassword';
GRANT ALL PRIVILEGES ON llamaman.* TO 'llamaman'@'%';
```

```yaml
environment:
  - DATABASE_URL=mysql+pymysql://llamaman:yourpassword@host:3306/llamaman
```

Таблиците се създават автоматично при първото свързване. Журналът на заявките отива в таблицата `request_log` вместо в JSON директорията `request_log/` (`RECORDINGS_DIR` няма ефект при MariaDB).

Метаданните за моделите на ниво възел (изходно хранилище + хеш на съдържанието) се пазят в таблицата `model_files` с ключ `(node_id, model_path)`. При обновяване всеки възел копира собствените си записи от стария общ блок с настройки (само пътища, които съществуват на неговия диск) и запазва блока като резервен източник за четене и път за връщане назад. Миграциите се версионират по възел.

> **Бележка за InnoDB:** `(node_id, model_path)` е `(64 + 700) × 4 = 3056` байта при utf8mb4, малко под лимита от 3072 байта за индекс в InnoDB, затова таблицата се създава с `ROW_FORMAT=DYNAMIC`.

MariaDB е също предпоставка за [Клъстериране](CLUSTERING.md) и за [Базата знания](KNOWLEDGE-BASE.md).

<a id="surviving-a-database-outage-local-mirror"></a>
## Оцеляване при срив на базата данни (локално огледало)

*По избор, изключено по подразбиране.*

При зададен `DATABASE_URL` базата данни е на критичния път на **всяка** заявка (проверките за удостоверяване четат настройките и проверяват API ключовете при всяко извикване). Ако стане недостъпна, възелът спира да обслужва, а рестарт на контейнера по време на срива изобщо не може да стартира.

Включете **Settings → App settings → "Keep a local mirror of the database"** (или задайте `LLAMAMAN_DB_MIRROR=1`) и възелът ще поддържа копие със запис в реално време в `DATA_DIR/db_mirror/`.

| Продължава да работи офлайн | Блокирано офлайн |
|---|---|
| Целият inference (и двата порта) | Създаването на първия потребител (`/setup`) - чисто нова инсталация така или иначе няма огледало, към което да се върне |
| Стартиране / спиране / приспиване / събуждане на модели | |
| Изтегляния, хеширане на модели и проверки за обновления | |
| Създаване и редактиране на **пресети** (включително за току-що изтеглени модели) | |
| Създаване и отнемане на **API ключове** | |
| Промяна на **настройките** за изтегляния и приложението | |
| Добавяне и премахване на **Hugging Face токени** | |

Офлайн промените отиват в журнал само за добавяне и се възпроизвеждат при повторно свързване (проверка на всеки 10s). Възпроизвеждането записва *редакцията*, а не получения ред, така че промяна, направена от друг възел по време на срива, оцелява (различно поле на пресет, различен ключ в настройките, различен HF токен - всички остават непокътнати).

**Изисквания и уговорки:**

- **`DATA_DIR` трябва да е постоянен том** (вече е такъв в примерния compose файл).
- **Всеки възел има нужда от собствен `DATA_DIR`.** Огледалото е маркирано с id на притежаващия възел; два възела, споделящи едно, изключват огледалото, вместо да повредят някой от изгледите.
- **Тайните попадат на локалния диск.** Настройките се копират дословно; **Hugging Face токените се огледалират в чист текст.** Паролите и API ключовете вече са хеширани. Ако сте избрали MariaDB отчасти, за да държите тайните извън отделните хостове, именно този компромис е причината функцията да е по избор.
- **Балансирането между възлите спира по време на срив.** Информацията кои пиъри са живи е в базата данни; деградирал възел вижда само себе си.
- **Промените по API ключовете са локални до повторното свързване.** Ключ, създаден офлайн, работи само на този възел; ключ, **отнет** офлайн, остава валиден на другите възли до повторното свързване. Планирайте отнеманията съответно.
- **Журналът на заявките се изхвърля, а не буферира,** докато сте офлайн (записите съдържат пълните тела; натрупването им през дълъг срив може да запълни тома).
- **Изключването на огледалото по време на срив се отлага** до повторното свързване.
- Миграциите на схемата никога не се изпълняват в деградирал режим; изпълняват се срещу реалната база данни при повторно свързване, преди възпроизвеждането на журнала.

## Променливи на средата

### Основни

| Променлива | По подразбиране | Описание |
|---|---|---|
| `LLAMAMAN_NODE_NAME` | *(задължителна)* | **Задължителна.** Уникална стабилна идентичност - ключ за разделяне на съхраненото състояние и идентичност в клъстера. Произволен низ; изберете веднъж и не го сменяйте (по-късна смяна осиротява съхраненото състояние). |
| `MODELS_DIR` | `/models` | Директория, сканирана за файлове с модели (път в контейнера) |
| `DATA_DIR` | `/data` | Директория за постоянна конфигурация/състояние (JSON файлове) |
| `RECORDINGS_DIR` | `{DATA_DIR}/request_log` | Директория за записите от журнала на заявките по разговори. Само за JSON бекенда; игнорира се при зададен `DATABASE_URL` |
| `LOGS_DIR` | `/tmp/llama-logs` | Директория за логове на инстанции и изтегляния (път в контейнера) |
| `HOST_MODELS_DIR` | *(като `MODELS_DIR`)* | Абсолютен път **на хоста** на тома с модели. Трябва да съвпада с лявата страна на `-v /host/path:/models` - подава се на Docker демона при стартиране на съседни контейнери |
| `HOST_LOGS_DIR` | *(като `LOGS_DIR`)* | Абсолютен път на хоста на тома с логове. Същото изискване като за `HOST_MODELS_DIR` |
| `ARCHIVE_DIR` | *(не е зададена)* | Път в контейнера, където е монтиран архивен том (напр. `/archive`). Задаването ѝ включва [Архив на модели](MODELS.md#model-archive); ако не е зададена, функцията е скрита |
| `PORT_RANGE_START` / `PORT_RANGE_END` | `8000` / `8020` | Пул от публични портове за llama-server/прокси |
| `INTERNAL_PORT_RANGE_START` / `INTERNAL_PORT_RANGE_END` | `9000` / `9020` | Пул от вътрешни портове, използван при включен прокси режим |
| `LLAMAMAN_PROXY_PORT` | `42069` | Порт на Ollama-съвместимото прокси |
| `LLAMAMAN_MAX_MODELS` | `0` | Максимален брой едновременни чат модели през проксито (LRU изместване; 0 = без лимит). Правила: [Изместване на модели](MODELS.md#model-eviction) |
| `LLAMAMAN_IDLE_TIMEOUT` | `0` | Минути до idle timeout за инстанции, управлявани от прокси (0 = изключено) |
| `LLAMAMAN_PDF_MAX_CONCURRENT` | `4` | Максимален брой едновременни растеризации на PDF в целия процес. Всяка растеризация стартира poppler + няколкостотин MB временна RAM при висок DPI |
| `SECRET_KEY` | *(авто)* | Тайна за сесиите на Flask. Ако не е зададена, се извежда от machine-id. Задайте я при внедрявания с няколко реплики |
| `SESSION_COOKIE_NAME` | `llamaman_session` | Име на сесийната бисквитка. С префикс, за да съжителства llamaman с други Flask приложения на същия хост - бисквитките се ограничават по хост+път, не по порт |
| `DATABASE_URL` | *(не е зададена)* | Низ за връзка с MariaDB/MySQL. Не е зададена = JSON файлове |
| `LLAMAMAN_DB_MIRROR` | *(не е зададена)* | Принудително включва (`1`) / изключва (`0`) локалното огледало на БД, като надделява над настройката на ниво възел. Има смисъл само с `DATABASE_URL` |
| `HEALTH_CHECK_TIMEOUT` | `3` | Таймаут в секунди за проверките на здравето на инстанциите |
| `MODEL_LOAD_TIMEOUT` | `300` | Секунди изчакване модел да стане здрав. Увеличете за много големи модели |
| `REQUEST_TIMEOUT` | `300` | Таймаут за **четене** в секунди за заявки към llama-server, препращане между възли и изчакване на портата. **Не** управлява времето за свързване с пиъри (отделен лимит от 5s) |

<a id="clustering"></a>
### Клъстериране

По избор. `LLAMAMAN_NODE_NAME` (в Основни) служи и като идентичност в клъстера и е задължителна за всички инсталации.

| Променлива | По подразбиране | Описание |
|---|---|---|
| `CLUSTER_ENABLED` | `false` | Задайте истинна стойност, за да присъедините този възел към клъстер. Изисква `CLUSTER_SECRET`; игнорира се с предупреждение, ако тайната е празна |
| `CLUSTER_SECRET` | *(не е зададена)* | Общ bearer токен (`X-Cluster-Secret`) за целия HTTP трафик между възлите. Еднакъв на всеки възел. Използвайте дълга случайна стойност в доверена мрежа или зад TLS |
| `CLUSTER_ADVERTISE_URL` | *(не е зададена)* | Как пиърите достигат UI/API на **този** възел - име на хост/IP, достъпно от другите хостове (не `localhost`). Без него възелът е само за преглед |
| `CLUSTER_NODE_ONLINE_WINDOW_S` | `45` | Секунди от последния heartbeat, след които възелът се показва като офлайн. Увеличете, ако възлите „мигат“ при натоварване или разминаване на часовниците |
| `LLAMAMAN_PERF_LOG` | *(изключено)* | Диагностика. Задайте истинна стойност, за да се логват времената по фази (`perf <name> <ms>`) за подозрително бавни пътища: спиране на отдалечена инстанция, препращания през клъстерното прокси, проверки за достъпност, моментна снимка за heartbeat, проверки за удостоверяване, `save_state`, статистика на контейнерите. Изключено по подразбиране; пренебрежимо натоварване, когато е изключено |
