# База знания и MCP

Съхранявайте документи, групирани по **теми**, а llamaman ги разделя на части (~1200 знака, по границите на абзаците, с припокриване 200), изчислява ембединги и съхранява векторите във вашата база данни MariaDB (колони `VECTOR` + ANN индекс по косинусово разстояние). След това всеки MCP клиент (Claude Desktop, Claude Code, агенти) може да търси в тях по смисъл. Всичко работи на хардуера, който вече имате: ембедингите идват от llama.cpp инстанция, стартирана с включено **Embedding model**, векторите са във вашата база данни, а MCP ендпойнтът се обслужва от самия llamaman.

**Изисквания:** бекендът MariaDB (`DATABASE_URL`, вижте [Бекенди за съхранение](CONFIGURATION.md#storage-backends)) на сървър **11.8+**, където се появява `VECTOR`. При JSON бекенда или по-стара MariaDB табът MCP обяснява защо базата знания не се поддържа и включването ѝ се отказва; нищо друго не се променя. Миграция няма: таблиците `kb_*` се създават при първа употреба.

**Настройка:**

1. Стартирайте инстанция с включено **Embedding model**. Работи всеки ембединг GGUF (`bge-m3`, `nomic-embed-text`, …).
2. **Settings → MCP** → включете **Knowledge base** и изберете модела в **Embedding model**. Падащото меню изброява всички модели с включен ембединг в клъстера.
3. Добавяйте документи с MCP инструмента `kb_ingest_document` (включете **Allow ingest over MCP**) или с `POST /api/kb/documents` от сесия с вход. Табът изброява, филтрира и изтрива теми и има тестово търсене, но все още няма форма за добавяне.
4. Включете **Expose over MCP**. Табът показва URL адреса на ендпойнта (`http://<your-host>:42069/mcp/knowledge`), а **Copy config.json** копира готова за поставяне конфигурация за клиента:

```json
{
  "mcpServers": {
    "llamaman-kb": {
      "type": "http",
      "url": "http://my-nas:42069/mcp/knowledge",
      "headers": { "Authorization": "Bearer <your-api-key>" }
    }
  }
}
```

Блокът `headers` е нужен само когато се изисква ключ (вижте режимите на достъп по-долу).

**Инструменти.** `kb_list_topics`, `kb_list_documents`, `kb_search` (откъси, подредени по релевантност, оценка 0–1) и `kb_get_document` са винаги налични. `kb_ingest_document` (създава темата, ако липсва; 200 KB на извикване; повторно подаване на идентично съдържание не прави нищо) се появява само при включено **Allow ingest over MCP**. `kb_delete_document` / `kb_delete_topic` се появяват само при включено **Allow delete over MCP**. Изтриването на тема изтрива документите ѝ, а изтриванията не могат да се отменят.

**Режими на достъп** (**MCP access**):

- **Global** (по подразбиране): всички клиенти работят с **общия пул** - виждат го и, ако добавянето/изтриването е позволено, го редактират. Новите теми отиват в общия пул. Удостоверяването следва **Require Authentication** (таб API Keys): включено означава, че се изисква валиден API ключ, изключено - ендпойнтът е отворен.
- **Per API key**: всяка заявка изисква валиден API ключ, дори при изключено Require Authentication. Темите, създадени от даден ключ, са **лични** за него, и два ключа могат да имат тема с едно и също име. Всеки ключ вижда и общия пул **само за четене**: може да търси и чете в него, но не и да добавя или изтрива. Темите и документите на други ключове се връщат като "not found".

Смяната на режима никога не мести и не изтрива данни, а личните теми остават лични и в двата режима. Преминаването Global → Per API key превръща всичко съществуващо в общ пул. Преминаването Per API key → Global скрива личните теми от всички клиенти, докато не превключите обратно. Табът MCP винаги показва всичко, като маркира всяка тема с `shared` или с името на притежаващия ключ. `POST /api/kb/topics` може също да създаде лична тема за даден ключ (`owner_key_id`), което е полезно, когато добавянето през MCP е изключено.

**Ембединг модел.** Изборът е по име на модела, не по инстанция. Всяко извикване за ембединг се изпълнява на първото от:
1. здрава инстанция на този възел;
2. заспала или спряна инстанция на този възел, която се събужда (или такава, която вече стартира и се изчаква);
3. пиър възел, който има включени и **Knowledge base**, и **Expose over MCP** и има модела (заспала инстанция там се събужда);
4. повторно стартиране на възела, който последно го е обслужвал, най-много 3 опита на 10 минути.

Първият ембединг записва размерността на вектора. Модел с различна размерност се отказва, докато не натиснете **Re-embed everything** - фонова задача, която изгражда наново частите на всеки документ (по една задача наведнъж, защитена от заключване в БД за целия клъстер). Проверява се само размерността, така че направете повторния ембединг сами, когато сменяте два модела с еднаква размерност.

**Бележки за клъстера.** Темите и документите са общи данни за клъстера в общата база данни, а не по възел. Всеки възел вижда една и съща база знания и MCP ендпойнтът на всеки възел я обслужва. Вижте [Клъстериране](CLUSTERING.md).

**Когато е изключена**, `/mcp/knowledge` връща 404 и в двата режима на достъп, и никоя заявка не докосва таблиците на базата знания.

> **Сигурност:** `/api/kb/*` е само за администратори: приемат се UI сесии с вход и пиъри от клъстера, а заявки, удостоверени с API ключ, получават 403. API ключовете обаче не са ограничени до базата знания: ключ, даден на MCP клиент, може да извиква и inference ендпойнтите и повечето други пътища `/api/*`. Използвайте отделен ключ за всеки клиент и го отнемете при съмнение.
