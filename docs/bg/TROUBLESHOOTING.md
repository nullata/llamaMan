# Отстраняване на проблеми

Пълната таблица симптом → решение. В [README](../../README.md#troubleshooting) са деветте най-чести реда при първо стартиране; всичко останало е тук.

| Симптом | Решение |
|---|---|
| Инстанцията е заседнала на **starting** | Проверете логовете с бутона Logs. Чести причини: OOM, грешка в пътя на модела, повреден GGUF, неизтеглен образ |
| _"Docker image not found"_ | Изтеглете съответния образ: `docker pull ghcr.io/ggml-org/llama.cpp:server-cuda` (или `server-rocm` / `server-sycl` / `server`) |
| _"Docker API error"_ при стартиране | Уверете се, че `/var/run/docker.sock` е монтиран (по подразбиране в `docker-compose.yml`) |
| Няма GPU / CUDA грешка | Уверете се, че NVIDIA Container Toolkit е инсталиран и `docker run --gpus all` работи на хоста |
| Няма GPU / ROCm грешка | Уверете се, че `/dev/kfd` и `/dev/dri` съществуват и потребителят ви е в `video`/`render` |
| Няма GPU / Intel Arc грешка | Уверете се, че `/dev/dri` е достъпен и потребителят ви е в `video`/`render` |
| Vulkan образът дава _"Unable to find group render"_ | Задайте `GPU_TYPE=vulkan`, за да може llamaMan да закачи render/video GID-овете на хоста числово (group_add по име се проваля при образи, чийто /etc/group няма запис `render`) |
| Няма статистика за GPU | NVIDIA: разкоментирайте блока `deploy.resources.reservations`. AMD/Intel: уверете се, че `/sys/class/drm:ro` е монтиран |
| Разпознат е грешен производител на GPU | Задайте `GPU_TYPE=cuda`/`rocm`/`intel` ръчно |
| Инстанцията е заседнала на **starting** при bare-metal | Контейнерът е здрав, но llamaman не може да го достигне. Задайте изрично `LLAMAMAN_IN_DOCKER=false`/`true`, ако автоматичното разпознаване греши за вашата среда |
| Strata: _"Docker image 'strata:latest' not found"_ | Изтеглете или компилирайте Strata образ в Settings → Docker Images (или `docker build -t strata .` в клонинг на хранилището на Strata). Вижте [Strata](STRATA.md) |
| Strata моделите не се показват | Задайте `STRATA_ENABLED=true`; възелът трябва да е NVIDIA (`GPU_TYPE=cuda`, ако разпознаването се провали). `GET /api/engines` показва причината |
| Strata инстанцията е заседнала на **starting** | Нормално е да отнеме минути при първо стартиране (изтегляне + пакетиране). Картата показва етапа; логът показва настройката на Strata. "setup failed" означава, че настройката е спряла - прочетете реда `[X]` в лога |
| Прозорецът със статистика е празен | Включете **Settings → App Settings → Request recording** (вижте [Записване на заявки и статистика](CONFIGURATION.md#request-recording--stats)) |
| Стартирането се проваля с GPU/CDI грешка на хост без GPU passthrough | Задайте **GPU Layers** на `0` за режим само с CPU без закачено GPU устройство или оправете GPU runtime-а |
| Конфликт на портове | Формата сама предлага свободен порт; коригирайте при нужда |
| Моделът не се показва в OpenWebUI | Уверете се, че `OLLAMA_BASE_URL=http://llamaman:42069`. Проверете дали `/api/tags` връща модели |
| OpenWebUI получава 401 | `require_auth` е включено (по подразбиране). Създайте API ключ и задайте `OPENAI_API_KEYS` в OpenWebUI |
| OpenAI клиент получава 503, когато моделите са пълни | Достигнат е лимитът `LLAMAMAN_MAX_MODELS`, а OpenAI API по подразбиране не може да измества. Вдигнете лимита или включете превключвателите за изместване: [Изместване на модели](MODELS.md#model-eviction) |
| Контейнерите не се почистват след спиране | llamaMan премахва контейнерите при спиране. Сираци след срив: `docker ps --filter name=llamaman-` или рестартирайте llamaMan (осиновяването на сираци се изпълнява при старт) |
| Клиентът (Hermes / OpenWebUI / др.) отчита обучителния контекстен прозорец вместо лимита от пресета | Обновете до 1.1.2+. `/api/ps` вече включва `context_length` със стойността на runtime ctx, с който е стартирана инстанцията, а `model_info["<arch>.context_length"]` в `/api/show` се презаписва с ефективния лимит |
| Клиент, питащ за име на група с обща опашка, получава собствения си ctx по подразбиране (напр. 128k) вместо реалния ctx на внедряването | `/api/show` и `/v1/models` вече отговарят за група с обща опашка на всеки възел в клъстера — дори без локален член — като използват runtime ctx на пиъра от общото състояние. Групите с няколко члена отчитат минимума сред активните членове, така че обявената стойност е безопасна за всяка цел на разпределението. Вижте [Клъстериране](CLUSTERING.md) |
