# База знаний и MCP

Храните документы, сгруппированные по **темам**, и llamaman нарезает их на чанки (~1200 символов, по границам абзацев, с перекрытием 200), вычисляет их эмбеддинги и сохраняет векторы в вашей базе MariaDB (колонки `VECTOR` + ANN-индекс по косинусному расстоянию). Любой MCP-клиент (Claude Desktop, Claude Code, агенты) сможет затем искать по смыслу. Всё работает на железе, которое у вас уже есть: эмбеддинги берутся из запущенного вами инстанса llama.cpp с включённым **Embedding model**, векторы живут в вашей базе, а сам MCP-эндпоинт раздаёт llamaman.

**Требования:** бэкенд MariaDB (`DATABASE_URL`, см. [Бэкенды хранения](CONFIGURATION.md#storage-backends)) на сервере **11.8+**, именно там и появился `VECTOR`. На JSON-бэкенде или более старой MariaDB вкладка MCP объясняет, почему база знаний не поддерживается, а включение отклоняется; больше ничего не меняется. Миграции нет: таблицы `kb_*` создаются при первом использовании.

**Настройка:**

1. Запустите инстанс с включённым **Embedding model**. Подойдёт любой embedding-GGUF (`bge-m3`, `nomic-embed-text`, …).
2. **Settings → MCP** → включите **Knowledge base** и выберите модель в **Embedding model**. Выпадающий список показывает все модели с embedding по всему кластеру.
3. Добавляйте документы через MCP-инструмент `kb_ingest_document` (включите **Allow ingest over MCP**) или `POST /api/kb/documents` из вошедшей сессии. Вкладка перечисляет, фильтрует и удаляет темы, есть тестовый поиск, но формы добавления пока нет.
4. Включите **Expose over MCP**. Вкладка показывает URL эндпоинта (`http://<your-host>:42069/mcp/knowledge`), а **Copy config.json** копирует готовую к вставке конфигурацию клиента:

```json
{
  "mcpServers": {
    "llamaman-kb": {
      "type": "http",
      "url": "http://my-nas:42069/mcp/knowledge",
      "headers": { "Authorization": "Bearer <your-api-key>" }
    }
  }
}
```

Блок `headers` нужен только когда требуется ключ (см. режимы доступа ниже).

**Инструменты.** `kb_list_topics`, `kb_list_documents`, `kb_search` (фрагменты в порядке убывания релевантности, score 0–1) и `kb_get_document` доступны всегда. `kb_ingest_document` (создаёт тему, если её нет; 200 КБ за вызов; повторная отправка идентичного содержимого — no-op) появляется только с включённым **Allow ingest over MCP**. `kb_delete_document` / `kb_delete_topic` появляются только с включённым **Allow delete over MCP**. Удаление темы удаляет её документы, и удаления необратимы.

**Режимы доступа** (**MCP access**):

- **Global** (по умолчанию): каждый клиент работает с **общим пулом**, видит его и, если разрешены ingest/delete, редактирует его. Новые темы попадают в общий пул. Аутентификация следует за **Require Authentication** (вкладка API Keys): включено — требуется валидный API-ключ, выключено — эндпоинт открыт.
- **Per API key**: каждый запрос требует валидный API-ключ, даже при выключенном Require Authentication. Темы, созданные ключом, **приватны** для этого ключа, и два ключа могут иметь тему с одинаковым именем. Каждый ключ также видит общий пул **только для чтения**: его можно искать и читать, но нельзя добавлять в него или удалять из него. Темы и документы других ключей возвращаются как "not found".

Переключение режимов никогда не перемещает и не удаляет данные, и приватные темы остаются приватными в обоих режимах. Переход Global → Per API key превращает всё существующее в общий пул. Переход Per API key → Global скрывает приватные темы от всех клиентов, пока вы не переключитесь обратно. Вкладка MCP всегда показывает всё, помечая каждую тему как `shared` или именем владеющего ключа. `POST /api/kb/topics` также может создать приватную тему для заданного ключа (`owner_key_id`), что удобно, когда MCP-ingest выключен.

**Модель эмбеддингов.** Выбор идёт по имени модели, не по инстансу. Каждый вызов embed выполняется на первом из:
1. здорового инстанса на этом узле;
2. спящего или остановленного инстанса на этом узле — его будят (или уже стартующего — его ждут);
3. узла-пира, у которого включены и **Knowledge base**, и **Expose over MCP** и который имеет эту модель (спящую там разбудят);
4. перезапуска на узле, который обслуживал её последним, не более 3 попыток за 10 минут.

Первый embed записывает размерность вектора. Модель с другой размерностью отклоняется, пока вы не нажмёте **Re-embed everything** — фоновую задачу, перестраивающую чанки каждого документа (одна задача за раз, под общекластерной блокировкой БД). Проверяется только размерность, так что при переключении между двумя моделями одинаковой размерности запускайте переэмбеддинг вручную.

**Заметки о кластере.** Темы и документы — общекластерные данные в общей базе, а не по узлам. Каждый узел видит одну и ту же базу знаний, и MCP-эндпоинт на любом узле её раздаёт. См. [Clustering](CLUSTERING.md).

**Когда выключено**, `/mcp/knowledge` возвращает 404 в обоих режимах доступа, и ни один запрос не трогает таблицы базы знаний.

> **Безопасность:** `/api/kb/*` доступен только админам: вошедшие UI-сессии и кластерные пиры допускаются, запросы, аутентифицированные API-ключом, получают 403. Но API-ключи не ограничены базой знаний: ключ, который вы дали MCP-клиенту, также может вызывать инференс-эндпоинты и большинство других маршрутов `/api/*`. Используйте отдельный ключ на каждый клиент и отзывайте его при сомнениях.
