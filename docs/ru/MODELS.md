<a id="models"></a>
## Модели

Кладите модели в том `/models` как `.gguf`-файлы, каталоги репозиториев HuggingFace (с `config.json`) или жмите **Download** в UI.

<a id="display-name"></a>
### Отображаемое имя

По умолчанию модели перечисляются по основе имени GGUF-файла. Каждой модели можно дать дружелюбное **Display Name** (в форме запуска). Когда задано, это id, который API-клиенты видят в `/api/tags` и `/v1/models`, поэтому OpenWebUI покажет `Qwen 2.5 14B` вместо `Qwen2.5-14B-Instruct-Q4_K_M`. Должно быть уникальным и не конфликтовать с именем файла другой модели или названием кластерной группы очереди.

<a id="model-updates"></a>
### Обновления моделей

Кнопка **Check for updates** (показывается для моделей с известным исходным репозиторием) сравнивает локальный файл с опубликованным хэшем содержимого репозитория:

- **Up to date** — записанный хэш совпадает
- **Update available** — перетягивает в staging-папку и атомарно подменяет только по завершении загрузки (неудачная подтяжка оставляет текущую модель нетронутой). Отказывается с 409, пока модель загружена.
- **Verify hash** — хэширует локальный файл (фоновая задача с прогрессом), когда хэш ещё не записан

Фоновое сканирование по opt-in (**Settings → Download Settings**, см. [Настройки загрузок](#download-settings)) держит эти ответы заготовленными заранее.

<a id="decision-models"></a>
## Decision-модели

Decision-модели отвечают на типизированные вопросы о входе вероятностями вместо генерации текста: System One API, представленный Jev'ом из TypeSafe, обслуживается llama.cpp (образы, собранные после 2026-10-05) на `POST /v1/systemone`. Открытые GGUF: Julia-1, Laya, Kev-4B, lev, Clef-Flash, Clef, OpenJev (OpenJev и Clef также принимают изображения, со своим `--mmproj`). llama-server распознаёт их по `<arch>.decision.type` в GGUF; флаг не нужен.

- **Определение.** Выбор такой модели в форме запуска говорит об этом под Model Path. Без пресета форма для неё заполняется: **Exclude from Max Models** вкл, **Web UI** выкл (её chat-страница не может управлять моделью), **Parallel Slots** `8` (каждый вопрос запроса занимает слот, и они делят вход), **Embedding Model** выкл (llama.cpp сам включает embedding-режим там, где модели нужно; принудительно не требуется). Encoder-модель (BERT-стиля) также получает Context, Batch и Micro-batch Size, равные её длине контекста: весь её вход должен влезть в один микро-батч. **Clef** (и Clef-Flash) задаёт все вопросы в одном промпте и считывает их за один проход, поэтому получает **Parallel Slots** `1` и Batch = Micro-batch = Context (16384, его обученный дефолт, когда Context пуст): весь запрос (вход, каждый вопрос и вариант) должен влезть в один микро-батч, иначе llama-server ответит "increase the physical batch size".
- **Маршрутизация.** `POST :42069/v1/systemone` выбирает модель по `"model"` как `/v1/chat/completions` (автозапуск, правила вытеснения, кластерная пересылка, очередь). Запрос пересылается без изменений (никаких переопределений sampling). На собственном порту инстанса он проходит через очередь per-instance прокси, когда тот работает.
- **Chat-эндпоинты их отвергают** (HTTP 422) — они не генерируют текст.
- **Request log:** ответы, и `input_tokens` как токены промпта (`output_tokens` всегда 0).
- **Ошибки:** вопрос, чьи варианты не влезают в один батч, отвергается llama-server ("increase the physical batch size") — поднимите Batch Size / Micro-batch Size.

```bash
curl http://localhost:42069/v1/systemone -H "Content-Type: application/json" -d '{
  "model": "Clef-Flash-Q4_K_M",
  "state": "Customer: I was charged twice for my order last week.",
  "questions": {
    "route":   {"type": "choice", "instructions": "Which team?", "criteria": {"billing": null, "shipping": null}},
    "angry":   {"type": "noul",   "instructions": "Is the customer angry?"},
    "urgency": {"type": "score",  "instructions": "How urgent?", "criteria": ["can wait", "today", "right now"]}
  }
}'
```

<a id="model-eviction"></a>
## Вытеснение моделей

`LLAMAMAN_MAX_MODELS` ограничивает одновременные **chat**-модели через прокси. Когда лимит заполнен и запрошена новая chat-модель, LRU chat-модель вытесняется:

| Запускающий | Вытесняет | Не может вытеснить |
|---|---|---|
| **Admin UI** | Сначала Ollama-managed (LRU), затем admin-launched | - |
| **Ollama API** | Ollama-managed (LRU) | Admin-launched *(по умолчанию)* |
| **OpenAI API** | Ничего *(по умолчанию; 503 при заполненном лимите)* | Всё *(по умолчанию)* |

Три переключателя в **Settings → App Settings** ослабляют эти дефолты:

- **Enforce `LLAMAMAN_MAX_MODELS` for admin UI launches** — молчаливое LRU-вытеснение перед запуском (сначала Ollama-managed). По умолчанию выкл → UI сначала спрашивает.
- **Allow Ollama API to evict admin-launched models** — fallback, когда Ollama-managed моделей нет. По умолчанию выкл.
- **Allow OpenAI API to evict admin-launched models** — даёт OpenAI API то же LRU-вытеснение, что Ollama. По умолчанию выкл.

Прочие детали:

- Считаются все работающие chat-инстансы (и admin UI, и управляемые через прокси).
- **Спящие инстансы тоже считаются** (занятый слот сохраняется во время idle-паузы) — но разбудить спящий инстанс ради его собственной модели лимит никогда не блокирует.
- Инстансы с **Exclude from Max Models** вкл (форма запуска) не считаются и не вытесняются никогда: embedding-модели, decision-модели, всё маленькое, что должно оставаться запущенным. Включение **Embedding Model** включает и это, а пресеты, сохранённые до появления переключателя, получают его из своей настройки Embedding Model.
- `LLAMAMAN_MAX_MODELS=0` полностью отключает вытеснение.

<a id="download-settings"></a>
## Настройки загрузок

В **Settings → Download Settings**:

- **Global speed limit (Mbps)** (0 = безлимит) — ограничивает каждую загрузку на этом узле и применяется к идущим загрузкам в пределах секунды. На узел: в кластере у каждого узла свой лимит (значение, сохранённое до того, как лимит стал поузловым, применяется ко всем узлам, пока тот узел не сохранит своё)
- **Auto-retry failed downloads** (по умолчанию выкл) + **Retry count per failed download** (по умолчанию 3)
- **Check models for updates in the background** (по умолчанию выкл) — opt-in воркер, спрашивающий каждый исходный репозиторий, был ли файл переопубликован, плюс вычисляющий контрольную сумму для любой модели, у которой её ещё нет. **Update check interval (hours)** по умолчанию 24. Хэширует максимум одну модель за проход; никогда не идёт, пока загрузка в процессе.

<a id="docker-image-management"></a>
## Управление Docker-образами

**Settings → Docker Images**: подтяните любой llama.cpp-образ по имени, удаляйте старые локальные образы (отключено для активного `LLAMA_IMAGE`, и возвращает ошибку, если Docker отказывает, потому что образ используется контейнером), и опционально автообновляйте llama.cpp-образы узла (`LLAMA_IMAGE` и каждый подтянутый там образ) по расписанию. Строка pull имеет выбор движка: при `STRATA_ENABLED` образ, подтянутый как *Strata*, попадает в *Manage Strata images* (дефолтного Strata-источника нет; впишите имя). **Pull repo & build latest** скачивает новейший коммит репозитория Strata (GitHub-тарбол, в `STRATA_SRC_DIR`) и собирает `STRATA_BUILD_IMAGE` через BuildKit посредством Docker-сокета. Автообновление самого Strata перетягивает подтянутые Strata-образы и, когда репозиторий был скачан, тянет его новейший коммит и пересобирает при изменении (или когда образ отсутствует); сам репозиторий оно никогда не скачивает. **Delete image & repo** убирает собранный образ (отказ, пока работающий инстанс его использует) и скачанный репозиторий — для узла, который гоняет подтянутый образ. Запуски Strata используют `STRATA_IMAGE`, когда он на узле, иначе собранный образ, иначе подтянутый. См. [Strata](STRATA.md).

<a id="model-archive"></a>
## Архив моделей

*(opt-in)* Перемещайте модели с быстрого хранилища на второй том и обратно через UI, вместо тасования файлов руками на хосте.

**Включите**, смонтировав архивный том в контейнер llamaMan и указав на него `ARCHIVE_DIR`:

```yaml
    volumes:
      - /opt/backup/llms:/archive
    environment:
      - ARCHIVE_DIR=/archive
```

Не задана — функция скрыта. llamaMan двигает файлы сам, поэтому `HOST_`-путь не нужен.

**Использование.**

- Наведите на модель в библиотеке и кликните архивную иконку.
- Архивированные модели остаются в списке, приглушённые, с бейджем *archived* и кнопкой **Restore**. Их нельзя выбрать для запуска, и они никогда не появляются в `/api/tags` / `/v1/models`.
- Перемещения видны в панели **Downloads** с прогрессом, скоростью и остатком времени, и могут быть отменены.
- Restore возвращает модель на исходный путь, поэтому пресеты, избранное, заметки и display names возвращаются вместе с ней.

**Что двигается.** Верхнеуровневая папка модели целиком под `/models`: папка загрузки со всеми шардами раздельного GGUF. `.gguf`, лежащий прямо в `/models`, двигается вместе со своими раздельными соседями. Папка шардов Strata-модели (`strata/<tag>`) двигается сама по себе.

**Безопасность.**

- **Тот же диск:** перемещение — мгновенный rename.
- **Между дисками:** llamaMan копирует в скрытую папку `.llamaman-partial-*` на назначении, fsync'ит, проверяет размер каждого файла, переименовывает на место и только затем удаляет источник.
- **Сбои:** отмена, провалившаяся проверка или мало свободного места оставляют источник нетронутым. Частичные копии, оставшиеся после перезапуска посреди перемещения, удаляются при старте.
- **Одно перемещение за раз.**
- **Отказ**, пока инстанс использует модель (включая спящий, или как draft-модель / mmproj, или Strata-инстанс, использующий шарды), пока загрузка пишет в неё, или когда имя на назначении уже существует. Запуск или удаление перемещаемой модели тоже отвергаются.

**Ограничения.** Задачи перемещения живут в памяти: после перезапуска llamaMan список пуст, и прерванное перемещение надо начинать заново (ничего не теряется). В кластерном режиме каждый узел архивирует на свой том, и кнопки показываются для узла, который вы просматриваете.

<a id="model-backup-and-restore"></a>
## Бэкап и восстановление моделей

**Settings → App Settings**:

- **Download Stored Models JSON** — экспортирует все просканированные модели + конфигурации пресетов в JSON с временной меткой
- **Restore from JSON** — по модели: уже присутствует → пресет вливается (существующие значения сохраняются); отсутствует, но есть источник HuggingFace → ставится в очередь на загрузку с предзаполненным пресетом; отсутствует и источник неизвестен → сообщается как невосстанавливаемая

<a id="cleanup-settings"></a>
## Настройки очистки

В **Settings → Cleanup Settings** (всё идёт периодически в фоне; только убирает/обновляет записи — файлы моделей никогда не удаляются):

- **Auto-clean completed/failed downloads** (по умолчанию 24ч) — активные загрузки не трогаются никогда
- **Auto-clean stopped instances** (по умолчанию 24ч) — работающие инстансы не убираются никогда
- **Auto-remove stale instance records** (по умолчанию интервал 5 мин) — перепроверяет записи `starting`/`healthy`/`sleeping` против Docker; записи, чей контейнер исчез, помечаются остановленными
