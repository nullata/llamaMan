# Кластеризация

> **Примечание:** это перевод, он может отставать от [английской версии](../en/CLUSTERING.md), которая является основной.

*Опционально, по умолчанию выключено — одноузловые установки вообще не затрагиваются.*

Несколько установок llamaMan работают как **один логический кластер**: единый дашборд, агрегирующий GPU, инстансы и загрузки каждого узла, с межузловыми запусками/подтягиваниями/загрузками и межузловым балансированием общей очереди. Узлы обнаруживают друг друга через общий бэкенд хранения — никакого попарного обмена ключами.

**Требования:**

- **Общий бэкенд хранения** — каждый узел смотрит на **один и тот же** `DATABASE_URL` (MariaDB/MySQL, см. [Бэкенды хранения](CONFIGURATION.md#storage-backends)). JSON хранится похостово и разделять его нельзя.
- **Уникальный `LLAMAMAN_NODE_NAME` на каждый узел** — кластерная идентичность узла (и всё равно обязательный для любой установки).
- **Один и тот же `CLUSTER_SECRET` на каждом узле** — bearer-токен (отправляется как `X-Cluster-Secret`) для всего межузлового HTTP.
- **`CLUSTER_ADVERTISE_URL` на каждый узел** для межузловых *действий* — hostname/IP, маршрутизируемый с **других** хостов (не `localhost`), например `http://srv1:5000`. Узел без него виден на дашборде, но только для просмотра.

Задаётся на **каждом** узле (различаются только `LLAMAMAN_NODE_NAME` и `CLUSTER_ADVERTISE_URL`):

```yaml
environment:
  - LLAMAMAN_NODE_NAME=srv1                 # unique per node
  - DATABASE_URL=mysql+pymysql://llamaman:pass@db-host:3306/llamaman   # identical
  - CLUSTER_ENABLED=true
  - CLUSTER_SECRET=a-long-shared-random-secret   # identical
  - CLUSTER_ADVERTISE_URL=http://srv1:5000  # this node's address, routable from peers
```

Каждый узел шлёт heartbeat примерно каждые 5 с; узел, молчащий дольше `CLUSTER_NODE_ONLINE_WINDOW_S` (по умолчанию 45 с), показывается как офлайн. Осмотр и управление — в **Settings → Cluster**.

Несколько настроек имеют область «на узел», потому что привязаны к хосту: отслеживаемые **Docker-образы**, переключатели вытеснения по лимиту моделей и [настройки пробуждения под нагрузкой](#waking-under-load). Всё остальное общее на весь кластер. Живые алиасы групп общей очереди рекламируются как выбираемые модели в `/api/tags` и `/v1/models` (с дедупликацией по кластеру), так что клиент может послать алиас, и запрос уйдёт на наименее загруженный узел, который его обслуживает.

**Длина контекста группы — общекластерная.** `/api/show` и `/v1/models` сообщают контекст группы очереди как **минимум по всем живым членам на узлах, способных принимать трафик**, независимо от того, к какому узлу обратился клиент. Члены на офлайн-узлах и узлах только для просмотра не учитываются. Группа с членами на разных значениях ctx рекламирует меньшее, чтобы промпт, под него подобранный, был безопасен для любой цели диспетчеризации — запас на более крупном члене просто не используется. Узел без локального члена группы всё равно отвечает (`context_length` берётся из рантайм-ctx пира в общем состоянии инстансов или из строки пресета в общей БД); группа без живых членов где бы то ни было по-прежнему возвращает 404 / без записи. Карточка инстанса в операторском UI добавляет `ctx <min>, capped by <node/model>`, когда ctx этого члена превышает рекламируемый минимум, чтобы было видно, какой пир тянет группу вниз.

> **Безопасность:** кластерный секрет позволяет любому пиру запускать действия на этом узле. Гоняйте межузловой трафик по доверенной сети или за TLS.

Переменные окружения, связанные с кластером: [Clustering variables](CONFIGURATION.md#clustering).

<a id="queue-groups"></a>
## Группы очередей

Группа очереди объединяет инстансы под одним **Queue group name**, чтобы клиент мог отправить это имя на любой узел. В таблице показано, что происходит с каждым членом с точки зрения другого узла:

| Состояние члена | В списках `/api/tags` и `/v1/models` | Получает маршрутизируемый трафик |
|---|---|---|
| Healthy | Да | Первый выбор |
| Запускается (загрузка) | Да | После healthy-членов |
| Спит | Да | Последним, только после всех бодрствующих, включая резервные. Запрос будит его. |
| Останавливается или остановлен | Нет | Никогда |
| На узле без `CLUSTER_ADVERTISE_URL` (только просмотр) | Нет | Никогда |
| На офлайн-узле (нет heartbeat 45 с) | Нет | Никогда |

**Для получения маршрутизируемой работы нужен `CLUSTER_ADVERTISE_URL`.** Без него узел по-прежнему может отправлять запросы пирам, но ни один из них не может до него достучаться.

**Сон и остановка здесь означают разное.** Тайм-аут простоя укладывает инстанс в сон, и спящий член просыпается, когда он нужен трафику. Остановленный член остаётся остановленным: к этому приводят остановка оператором, вытеснение и сбой, и никакой запрос с другого узла его не перезапустит. Запрос к узлу, который его держит, вернёт `503`, если только имя не совпадает с собственным файлом этого члена — тогда он всё равно проснётся.

<a id="waking-under-load"></a>
### Пробуждение под нагрузкой

Бодрствующие члены ставят запросы в очередь, а не отклоняют их, поэтому сам по себе трафик дошёл бы до спящего члена лишь после переполнения всей очереди. Поэтому llamaMan будит одного заранее. Когда все healthy-члены группы заполнены, запросы стоят в очереди и ничего не загружается в течение 3 опросов подряд (около 15 секунд), просыпается один спящий член. Во всём кластере это делает только узел с наименьшим именем среди держащих спящего члена, и не более одного члена на группу за опрос. Основной член просыпается раньше резервного.

Учитывается только спящий член, который добавит ёмкость: ему нужен **Max Concurrent** выше `0`, и он не должен делить очередь с бодрствующим членом на том же узле.

Пробуждение пропускается, с одной строкой в логе, если веса модели не помещаются в свободную VRAM узла. Проверка суммирует свободную память всех GPU и учитывает только веса, поэтому прошедшая её модель всё ещё может не загрузиться. Если VRAM прочитать не удаётся или у модели нет файла для измерения (виртуальные модели Strata), пробуждение выполняется.

Обе настройки задаются на уровне узла через `POST /api/settings`:

| Настройка | По умолчанию | Значение |
|---|---|---|
| `eager_wake_enabled` | `true` | Будит ли этот узел своих спящих членов под нагрузкой |
| `eager_wake_polls` | `3` | Число подряд идущих опросов с насыщением (по 5 секунд) до пробуждения |

<a id="when-a-group-cant-be-served"></a>
### Когда группу невозможно обслужить

Если группу размещают другие узлы, но ни один не может принять запрос, клиент получает ошибку с перечислением всех узлов и причин, а не "model not found":

| Статус | Код (маршруты OpenAI) | Значение |
|---|---|---|
| `429` | `group_full` | Очередь хотя бы одного пира заполнена. Повторная попытка может сработать. |
| `503` | `group_unavailable` | Пиры офлайн, только для просмотра, недоступны или не готовы. |

Узел-владелец возвращает эти коды `503` для своих членов, а входной узел, получив такой код, пробует следующего члена:

| Код | Значение |
|---|---|
| `model_stopping` | Член группы завершает работу |
| `group_stopped` | Все члены на этом узле остановлены |
| `wake_failed` | Пробуждение не удалось |
| `wake_timeout` | Член не стал healthy вовремя |

Имя группы не запускает локальный файл, в имени которого оно лишь содержится. Файл с точно таким именем по-прежнему запускается.

<a id="troubleshooting-a-group-that-isnt-visible"></a>
### Диагностика: группа не видна

- **Бэкенду JSON нужен один общий `DATA_DIR`.** Узлы находят друг друга через реестр, поэтому при раздельных каталогах каждый узел не видит пиров. Используйте MariaDB, если каталог действительно не общий.
- **Деградировавшая база намеренно скрывает пиров.** Пока чтение обслуживает зеркало БД, узел видит только себя и обслуживает запросы локально.
- **Неудачная проба нагрузки не скрывает группу.** Не ответивший пир остаётся маршрутизируемым по своему снимку (давностью до 45 секунд), но идёт после всех ответивших. В логе фиксируется, когда пробы к пиру начинают сбоить и когда восстанавливаются.
