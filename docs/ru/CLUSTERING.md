# Кластеризация

*Опционально, по умолчанию выключено — одноузловые установки вообще не затрагиваются.*

Несколько установок llamaMan работают как **один логический кластер**: единый дашборд, агрегирующий GPU, инстансы и загрузки каждого узла, с межузловыми запусками/подтягиваниями/загрузками и межузловым балансированием общей очереди. Узлы обнаруживают друг друга через общий бэкенд хранения — никакого попарного обмена ключами.

**Требования:**

- **Общий бэкенд хранения** — каждый узел смотрит на **один и тот же** `DATABASE_URL` (MariaDB/MySQL, см. [Бэкенды хранения](CONFIGURATION.md#storage-backends)). JSON хранится похостово и разделять его нельзя.
- **Уникальный `LLAMAMAN_NODE_NAME` на каждый узел** — кластерная идентичность узла (и всё равно обязательный для любой установки).
- **Один и тот же `CLUSTER_SECRET` на каждом узле** — bearer-токен (отправляется как `X-Cluster-Secret`) для всего межузлового HTTP.
- **`CLUSTER_ADVERTISE_URL` на каждый узел** для межузловых *действий* — hostname/IP, маршрутизируемый с **других** хостов (не `localhost`), например `http://srv1:5000`. Узел без него виден на дашборде, но только для просмотра.

Задаётся на **каждом** узле (различаются только `LLAMAMAN_NODE_NAME` и `CLUSTER_ADVERTISE_URL`):

```yaml
environment:
  - LLAMAMAN_NODE_NAME=srv1                 # unique per node
  - DATABASE_URL=mysql+pymysql://llamaman:pass@db-host:3306/llamaman   # identical
  - CLUSTER_ENABLED=true
  - CLUSTER_SECRET=a-long-shared-random-secret   # identical
  - CLUSTER_ADVERTISE_URL=http://srv1:5000  # this node's address, routable from peers
```

Каждый узел шлёт heartbeat примерно каждые 5 с; узел, молчащий дольше `CLUSTER_NODE_ONLINE_WINDOW_S` (по умолчанию 45 с), показывается как офлайн. Осмотр и управление — в **Settings → Cluster**.

Несколько настроек имеют область «на узел», потому что привязаны к хосту: отслеживаемые **Docker-образы** и переключатели вытеснения по лимиту моделей. Всё остальное общее на весь кластер. Живые алиасы групп общей очереди рекламируются как выбираемые модели в `/api/tags` и `/v1/models` (с дедупликацией по кластеру), так что клиент может послать алиас, и запрос уйдёт на наименее загруженный узел, который его обслуживает.

**Длина контекста группы — общекластерная.** `/api/show` и `/v1/models` сообщают контекст группы очереди как **минимум по всем живым членам**, независимо от того, к какому узлу обратился клиент. Группа с членами на разных значениях ctx рекламирует меньшее, чтобы промпт, под него подобранный, был безопасен для любой цели диспетчеризации — запас на более крупном члене просто не используется. Узел без локального члена группы всё равно отвечает (`context_length` берётся из рантайм-ctx пира в общем состоянии инстансов или из строки пресета в общей БД); группа без живых членов где бы то ни было по-прежнему возвращает 404 / без записи. Карточка инстанса в операторском UI добавляет `ctx <min>, capped by <node/model>`, когда ctx этого члена превышает рекламируемый минимум, чтобы было видно, какой пир тянет группу вниз.

> **Безопасность:** кластерный секрет позволяет любому пиру запускать действия на этом узле. Гоняйте межузловой трафик по доверенной сети или за TLS.

Переменные окружения, связанные с кластером: [Clustering variables](CONFIGURATION.md#clustering).
