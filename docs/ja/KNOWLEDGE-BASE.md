# ナレッジベースと MCP

ドキュメントを**トピック（topic）**ごとにグループ化して保存すると、llamaman がそれらをチャンク化（約1200文字、段落揃え、200文字オーバーラップ）し、埋め込み（embedding）を生成して、MariaDB データベースにベクトル（`VECTOR` 列 + コサイン ANN インデックス）として保存します。任意の MCP クライアント（Claude Desktop、Claude Code、エージェントなど）が意味に基づいたセマンティック検索を行えます。すべてがすでに運用中のハードウェア上で実行されます。埋め込みは **Embedding model** を有効にして起動した llama.cpp インスタンスから取得され、ベクトルはデータベースに保存され、llamaman 自体が MCP エンドポイントを提供します。

**要件:** `VECTOR` がサポートされたバージョン **11.8+** の MariaDB バックエンド（`DATABASE_URL`、[Storage Backends](CONFIGURATION.md#storage-backends) を参照）。JSON バックエンドまたは古い MariaDB の場合、MCP タブにナレッジベースが非対応である理由が表示され、有効化は拒否されます。それ以外の機能は影響を受けません。マイグレーションは不要で、`kb_*` テーブルは初回使用時に自動作成されます。

**セットアップ:**

1. **Embedding model** を有効にしてインスタンスを起動します。任意の埋め込み用 GGUF（`bge-m3`、`nomic-embed-text` など）が使用できます。
2. **Settings → MCP** → **Knowledge base** をオンにし、**Embedding model** でモデルを選択します。ドロップダウンにはクラスタ全体で埋め込みが有効になっているすべてのモデルが一覧表示されます。
3. MCP の `kb_ingest_document` ツール（**Allow ingest over MCP** をオンにする）、またはログイン済みセッションから `POST /api/kb/documents` を使用してドキュメントを追加します。タブにはトピックの一覧表示、フィルタリング、削除、テスト検索機能がありますが、追加フォームはまだありません。
4. **Expose over MCP** をオンにします。タブにエンドポイント URL（`http://<your-host>:42069/mcp/knowledge`）が表示され、**Copy config.json** をクリックすると貼り付け可能なクライアント設定がコピーされます:

```json
{
  "mcpServers": {
    "llamaman-kb": {
      "type": "http",
      "url": "http://my-nas:42069/mcp/knowledge",
      "headers": { "Authorization": "Bearer <your-api-key>" }
    }
  }
}
```

`headers` ブロックはキーが必要な場合にのみ必要です（後述のアクセスモードを参照）。

**ツール。** `kb_list_topics`、`kb_list_documents`、`kb_search`（スコア 0〜1 のスコア順でパッセージを返却）、`kb_get_document` は常に利用可能です。`kb_ingest_document`（トピックが存在しない場合は作成。1回の呼び出しあたり 200 KB。同一コンテンツの再送信は no-op）は **Allow ingest over MCP** がオンの場合にのみ表示されます。`kb_delete_document` / `kb_delete_topic` は **Allow delete over MCP** がオンの場合にのみ表示されます。トピックを削除するとそのドキュメントも削除され、元に戻すことはできません。

**アクセスモード**（**MCP access**）:

- **Global**（デフォルト）: すべてのクライアントが**共有プール**上で動作し、それを閲覧し、取り込み/削除が許可されていれば編集できます。新しいトピックは共有プールに追加されます。認証は **Require Authentication**（API Keys タブ）に従います。オンの場合は有効な API キーが必要で、オフの場合はエンドポイントが公開されます。
- **Per API key**: Require Authentication がオフであっても、すべてのリクエストに有効な API キーが必要です。キーによって作成されたトピックはそのキーに対して**プライベート**となり、2つのキーがそれぞれ同じ名前のトピックを持つことができます。また、各キーは共有プールを**読み取り専用**で参照できます（検索や読み取りは可能ですが、取り込みや削除は不可）。他のキーのトピックやドキュメントは「見つかりません」として返されます。

モードを切り替えてもデータが移動または削除されることはなく、プライベートトピックは両方のモードでプライベートのまま維持されます。Global → Per API key に移行すると、既存のすべてのデータが共有プールになります。Per API key → Global に移行すると、元に戻すまでプライベートトピックはすべてのクライアントから非表示になります。MCP タブには常にすべてが表示され、各トピックには `shared` または所有するキーの名前がラベル付けされます。`POST /api/kb/topics` は指定したキー用のプライベートトピック（`owner_key_id`）を作成することもでき、MCP からの取り込みが無効な場合に便利です。

**埋め込みモデル。** インスタンスではなくモデル名で選択します。各埋め込み呼び出しは、以下の優先順位で最初に利用可能なもので実行されます:
1. このノード上の正常なインスタンス。
2. このノード上のスリープ中または停止中のインスタンス（起動されます。起動中の場合は完了を待ちます）。
3. **Knowledge base** と **Expose over MCP** の両方がオンになっており、そのモデルを保持しているピアノード（スリープ中の場合は起動されます）。
4. 最後にそれを提供したノードでの再起動（10分間に最大3回試行）。

最初の埋め込み時にベクトルの次元数が記録されます。異なる次元数のモデルは、すべてのドキュメントのチャンクを再構築するバックグラウンドジョブである **Re-embed everything** を押すまで拒否されます（クラスタ全体の DB ロックによって保護され、一度に1つのジョブのみ実行）。次元数のみがチェックされるため、同じ次元数の2つのモデルを切り替える場合は、手動で再埋め込みを実行してください。

**クラスタに関する注意点。** トピックとドキュメントは、ノード単位ではなく共有データベース内のクラスタ全体のデータです。すべてのノードが同じナレッジベースを参照し、任意のノードの MCP エンドポイントがそれを提供します。[Clustering](CLUSTERING.md) を参照してください。

**無効時**、`/mcp/knowledge` は両方のアクセスモードで 404 を返し、いかなるリクエストもナレッジベーステーブルにアクセスしません。

> **セキュリティ:** `/api/kb/*` は管理者専用です。ログインした UI セッションおよびクラスタピアは受け入れられますが、API キーで認証されたリクエストは 403 になります。ただし、API キーはナレッジベースに限定されません。MCP クライアントに付与したキーは、推論エンドポイントや他のほとんどの `/api/*` ルートも呼び出すことができます。クライアントごとに専用のキーを使用し、疑わしい場合は失効させてください。
