## 起動フォームツール

起動フォームのアクション行の右側には、3つのツールボタンが配置されています:

- **Export preset** - 現在のフォームの値を JSON ファイルとしてダウンロード（ノード間で移植可能。ストレージには保存されません）。
- **Import preset** - プリセット JSON をフォームにロード。フィールドへの入力のみ行われます。保存するには Save Preset を押す必要があります。
- **Copy llama.cpp command** - 現在のフォームの値に対応する `llama-server ...` 呼び出しコマンドをクリップボードにコピー。実際の起動で使用されるフラグ生成コードと同じロジックでサーバーサイドレンダリングされるため、フラグの変更に自動追従します。

設定を折りたたんでいる場合、**Quick Launch** ボタンを押すと選択したモデルをプリセットから直接起動できます。

各インスタンスは、割り当てられたポートで OpenAI 互換 API を公開します。GGUF を選択すると、llamaMan はメタデータを読み取ってレイヤー数を検出し、**GPU Layers** の横に表示します（例: `/ 32`）。

| **Micro-batch Size** | `512` | `--ubatch-size` | GPU に送信される物理バッチサイズ。大きいほどプレフィルが速くなりますが VRAM を消費します。埋め込みモデルおよびエンコーダ（BERT スタイル）の意思決定モデルは、入力全体が1つのマイクロバッチに収まる必要があります。空欄時はフラグを省略 |

**GPU 設定 (GPU Settings)**

| 設定 | デフォルト | フラグ | 説明 |
|---|---|---|---|
| **GPU Layers** | `-1` | `--n-gpu-layers` / `--gpu-layers` / `-ngl` (エイリアス) | `-1` = **auto**（llama.cpp が VRAM を推定して決定。CPU にレイヤーを残す場合あり）。`-2` = **all**（全レイヤーを強制。収まらない場合は失敗）。`0` = CPU のみ、コンテナに GPU をアタッチしません。正の整数 N は最下層から正確に N レイヤーをオフロード |
| **MoE CPU Layers** | `0` | `--cpu-moe` / `--n-cpu-moe` | Mixture-of-Experts モデルでのみ意味を持ちます。`0` = 何も出力しない。`-1` = `--cpu-moe`（すべてのレイヤーのルーティングされたエキスパートの重みを CPU に固定）。正の整数 N = `--n-cpu-moe N`（最初の N レイヤーのエキスパートを CPU に配置）。大型 MoE ではエキスパートが重みの大半を占めるもののトークンごとに動作するのは一部であるため、VRAM を約 4〜10 倍削減。dense モデルでは無効: llama.cpp の正規表現（`\.ffn_(up\|down\|gate\|gate_up)_(ch\|)exps`）にマッチせず、オーバーライドは暗黙的に無視されます。**共有エキスパートは対象外**（DeepSeek-MoE / Qwen2-MoE / Hunyuan-MoE の `_shexp`）— これらには Extra Args で `-ot` オーバーライドを追加してください |
| **GPU Devices** | *(all)* | *(コンテナレベル)* | アタッチするカンマ区切りのホスト GPU インデックス（例: `0,1`）。コンテナ内では 0 から振り直されます。Intel Arc ではサポートされていません |
| **Split Mode** | `layer` | `--split-mode` | `none`（単一 GPU、Tensor Split を無視）/ `layer`（llama.cpp のデフォルト。レイヤー全体を分割）/ `row`（テンソル行を分割。通常、NVLink などの高速相互接続でのみ有効） |
| **Tensor Split** | *(auto)* | `--tensor-split` | コンテナから認識可能な GPU ごとのカンマ区切りの相対重み（例: `24,16`）。空欄時は起動時に各 GPU の合計 VRAM から自動入力。Split Mode = `none` または 1 つの GPU のみ認識可能な場合は無視されます |

| Presence Penalty | `0.0` | -2.0 〜 2.0 |
| Repeat Penalty | `0.0` | 0.0-2.0（`0` = 無効） |

## プリセットのリアルタイム更新

プリセットを保存すると、可能な場合は実行中のそのモデルのインスタンスをインプレースで更新します:

- **リアルタイム（再起動不要）:** `idle_timeout_min`、`max_concurrent`、`max_queue_depth`、`share_queue`、全6つのプロキシサンプリングフィールド、全5つのループ検出フィールド（次のリクエストから反映）
- **再起動が必要:** 起動時にコンテナに焼き込まれるすべての項目（GPU レイヤー、MoE CPU レイヤー、ctx サイズ、スレッド数、バッチスレッド数、キャッシュタイプ、flash-attn、reasoning フォーマット、ロードモード、DRY サンプラー、投機的デコーディングフィールド、埋め込みフラグ、mmproj/PDF フィールド、追加引数、メモリ制限）

**プロキシサンプリングの注意点:** インスタンスが `idle_timeout=0`、`max_concurrent=0`、`override_enabled=false` のすべてが設定された状態で起動された場合、サイドカープロキシは生成されません。その場合、後から `override_enabled=true` をリアルタイムで切り替えても、アプリの互換エンドポイント経由のリクエストにはオーバーライドが適用されますが、公開ポートへの直接アクセスはバイパスされます。その場合は再起動してプロキシを生成してください。

## 並行性とキューイング

**Max Concurrent** > 0 の場合、llamaMan はインスタンスの前に FIFO ゲートを配置します。超過したリクエストは **Max Queue Depth** まで待機し、それを超えると HTTP 429 を返します。ゲートの統計情報（アクティブ + キュー中）は API 経由で確認できます。

**Parallel vs Max Concurrent:** `Parallel` は llama-server 内部の KV スロットを制御し、`Max Concurrent` は llamaMan が一度に転送するリクエスト数を制限します。両方を併用（例: `Parallel=4`, `Max Concurrent=4`）することで、スロットをオーバーフローさせることなくサーバーに十分な負荷を供給し続けることができます。

## 画像と PDF の入力

**Image & PDF Input** トグルを有効にすると、ビジョンモデルのマルチモーダルプロジェクター（`--mmproj`）がメイン GGUF と一緒にロードされます。**MMPROJ Model** フィールドにはプロジェクター GGUF（一般的なファイル名: `mmproj-<model>-<precision>.gguf`）を指定します。

**mmproj を GPU にオフロード (Offload mmproj to GPU)**（デフォルトでオン）: llama.cpp は `--no-mmproj-offload` が指定されない限りプロジェクターを GPU 上に保持するため、*オン* はフラグを完全に省略し（このオプションが存在する前とバイト単位で同一の CLI）、*オフ* は `--no-mmproj-offload` を渡してビジョンエンコーダを CPU 上で実行します — エンコーダが数 GB を固定するような VRAM が逼迫した環境で有用です。

**PDF** は、llama-server（ネイティブ PDF サポートなし）に転送する**前**に各ページを PNG にラスタライズすることでサポートされます。インスタンスでこれを有効にするには、**Accept PDF uploads**（Image & PDF Input グループ内）をオンにします。親の **Image & PDF Input** トグルがグループ全体を制御するため、親をオフにすると PDF サブトグルもクリアされます（プロジェクターがなければラスタライズされたページを受け取るビジョンモデルがないため）。以下の両方で認識されます:

- **OpenAI**: `data:application/pdf;base64,...` URL を持つ `image_url`、または新しい `file` ブロック
- **Ollama**: `images[]` に混在した base64 PDF バイト — llamaMan が `%PDF-` を検知して PDF を展開します。通常の画像は既存のパスを維持します

**テキストレイヤーのショートカット (Text-layer shortcut)**（デフォルトはオフ）: **Try text layer first** がオンの場合、llamaMan はラスタライズの前に `pypdf.extract_text()` を実行します。十分なテキスト（ページあたり約50文字以上）を持つデジタルネイティブな PDF（Word/LaTeX/ブラウザ印刷）は、1つのテキストブロックとしてインライン化され、ビジョンパスを完全にスキップします。テキストがまばらな場合はラスタライズにフォールバックします。デフォルトでオフになっているのは、ラスタライズがビジョンモデルのためにレイアウトを維持すること、およびすべての PDF に対して予測可能な動作をすることが暗黙的なショートカットよりも好ましいためです。

**リクエストごとの上限:** `PDF DPI`（72〜600、デフォルト 200）および `Max PDF Pages`（1〜200、デフォルト 20）。上限を超える PDF は切り捨てられるのではなく、HTTP 400 を返します。

**ラスタライズの並行性:** PDF のレンダリングは CPU と RAM の負荷が高く、インスタンスごとのゲートの前に gunicorn ワーカープロセスのスレッドで実行されます。プロセス全体のセマフォが同時ラスタライズ数を制限します。`LLAMAMAN_PDF_MAX_CONCURRENT`（デフォルト 4）で調整可能です。

<a id="anti-loop"></a>
## ループ防止

起動フォームの **Anti-Loop** セクションにある2つの独立した制御項目で、両方ともデフォルトはオフです。これらは同じ問題（モデルが安定した出力ループにはまる現象）をパイプラインの異なる2つのポイントで対処します。最高の効果を得るには併用してください。

**DRY サンプラー（ソフト、サンプリング時）**。llama-server の `--dry-multiplier` / `--dry-base` / `--dry-allowed-length` / `--dry-penalty-last-n` にマッピングされます。最近現れた n-gram を延長するすべてのトークンはサンプリング時に確率のペナルティを受け、重複したスパンを出力する前にモデルが自己反復しないように誘導されます。これは*ソフト*な防御線であり、通常は散文に対してこれ単体で十分です。コンテナ起動時に焼き込まれるため、プリセットの編集には再起動が必要です。Multiplier = 0 で完全に無効化されます（llama.cpp 自身のデフォルト）。

*DRY サンプラー*（起動時に焼き込み — 再起動が必要）:

| 設定 | デフォルト | フラグ | 説明 |
|---|---|---|---|
| Multiplier | `0.8`（UI 表示値。`0` で無効） | `--dry-multiplier` | ペナルティの強さ。llama.cpp は `0` を無効として扱います |
| Base | `1.75` | `--dry-base` | 指数の底 ≥ 1.0 |
| Allowed Length | `2` | `--dry-allowed-length` | この長さまでの n-gram は免除されます |
| Penalty Last N | *(auto)* | `--dry-penalty-last-n` | ルックバックウィンドウ。空欄時はフラグを省略 |

**出力ループ検出（ハード、事後検出）**。DRY で十分でない場合（モデルが安定したアトラクターにはまり続ける場合）、llamaman のプロキシはクライアントにストリーミングされるアシスタント可視の出力テキスト（コンテンツ + 思考プロセス）を監視します。スキャンの周期ごと（デフォルト: インラインで 64 チャンクごと、および 10 秒のワーカーフォールバック）に、バッファの最後の `min_chunk_chars` 文字が反復されていないかチェックされます。`min_repetitions` 回以上現れた場合、ターンは強制終了されます:

- **llama-server への上流接続が切断されます** — llama-server のクライアント切断時停止機能が生成を中断し、次のリクエストのためにモデルを解放します。
- **合成終端マーカーがクライアントのストリームに注入されます** — OpenAI クライアントには `finish_reason=stop` かつ内容が `[llamaman: output loop detected, ending turn]` である最後のデルタが1つ届きます。Ollama クライアントには `done: true` 行に `done_reason: "loop_detected"` が表示されます。

*出力ループ検出*（プロキシ側。プリセットからリアルタイム更新 — 次のリクエストから新しいしきい値を適用）:

| 設定 | デフォルト | 説明 |
|---|---|---|
| Min chunk chars | `200` | 範囲 60〜4096。小さくするとより短いループを捕捉できますが、反復的だが正常なコンテンツで誤検出するリスクがあります |
| Min repetitions | `3` | 範囲 2〜20 |
| Buffer size (chars) | `8192` | 処理中リクエストあたりのローリングウィンドウ。範囲 512〜65536 |
| Scan every N chunks | `64` | インラインスキャン周期 |
| Fallback scan (seconds) | `10` | トークンの出力が遅すぎてインラインしきい値に達しないストリームのためのバックグラウンドワーカー |

**監視場所:**
- **`:42069` 上の互換ルート**（Ollama `/api/chat`、`/api/generate`; OpenAI `/v1/chat/completions`、`/v1/completions`）— 対象インスタンスのプリセットでトグルがオンになっている限り常に監視。
- **インスタンスごとのポート（`8000-8020`）** — そのインスタンスにサイドカープロキシがすでに存在する場合のみ（つまり Idle Timeout、Max Concurrent、または Proxy Sampling Overrides のいずれかもオンになっている場合）。ループ検出自体はサイドカープロキシを起動しないため、直接アクセスも監視するには他の3つのいずれかを有効にしてください。

**チューニング:**
- `min_chunk_chars`（60〜4096、デフォルト 200）— トリガーとなる最小反復周期。小さい値は短いループを捕捉しますが、反復的だが正常なコンテンツ（番号付きリスト、詩のリフレイン、Markdown テーブル）で誤検出するリスクがあります。60〜100 はアグレッシブ、200 は散文に適したバランスの取れたデフォルト、400+ は段落規模のループでのみトリガーされます。
- `min_repetitions`（2〜20、デフォルト 3）— 終了させるまでにチャンクの完全なコピーが何回出現する必要があるか。2 は二重反復でトリガー（アグレッシブ）、3〜5 は応答性と誤検出防止のバランスが取れています。
- `max_buffer_chars`（512〜65536、デフォルト 8192）— アクティブなリクエストごとに保持されるローリングウィンドウ。少なくとも `min_chunk_chars × min_repetitions` 以上である必要があります。
- `scan_every_n_tokens`（8〜4096、デフォルト 64）— インラインスキャン周期。小さいほど迅速に強制終了しますが CPU を消費します。
- `scan_interval_s`（1〜600、デフォルト 10）— インラインしきい値に達しなかったバッファをバックグラウンドワーカーが再スキャンする頻度。

ループ検出のしきい値の変更は*次の*リクエストから有効になります（処理中のストリームはアタッチ時に取得されたしきい値を維持します）。DRY の変更はフラグがコンテナに焼き込まれているため再起動が必要です。

**検出アルゴリズム**（v1）: バッファの最後の `min_chunk_chars` 文字をターゲットとし、正確な出現回数をカウントし、`min_repetitions` 以上の場合にフラグを立てます。表記揺れのある近似反復（繰り返しの間で句読点がわずかにずれる "The answer is: The answer is: The answer is:" など）は捕捉できません — これらは DRY のサンプリング時防御によって捕捉されます。意図的にシンプルかつ軽量に設計されています。

**防御的不変条件:** ストリーミングパス内のすべてのフックは、ログを記録して素通りする `try/except Exception` でラップされています — 検出器のバグによって実際のユーザーのストリームが壊れることは決してありません。

## インスタンスごとのプロキシ

インスタンスで **Idle Timeout**、**Max Concurrent**、または **Proxy Sampling Overrides** がオンになっている場合、llamaMan は llama-server コンテナの前に WSGI プロキシを挿入します: 公開ポート（例: 8000）がプロキシとなり、llama-server は別の内部ポートでリッスンします。プロキシは、モデル名の検証、スリープ中のインスタンスのリクエスト時復帰、`RequestGate` 並行性制限、およびサンプリングの挿入を行います。

**モデル名の検証:** 推論エンドポイントでリクエストボディに `"model"` フィールドがある場合、ロードされたモデルのファイル名幹（小文字、拡張子なし）と比較されます。**前方一致（プレフィックスマッチ）が許可されます**（例: `"qwen2.5-0.5b-instruct-q2"` は `"qwen2.5-0.5b-instruct-q2_k"` に一致）。不一致の場合は HTTP 404 を返し、スリープ中のインスタンスは起動しません。`"model"` フィールドがないリクエストは無条件で転送されます。

## アイドルタイムアウト

起動フォームで **Idle Timeout min** を設定します（0 = 無効）。有効にすると、リクエストがない状態が N 分間続いた後に llama-server コンテナが停止して VRAM が解放されます。次のリクエストで同じ設定の新しいコンテナが起動します。クライアント側からは同じポートが見え、コールドスタートの遅延のみが発生します。

プロキシ管理（OpenWebUI）のインスタンスの場合は、代わりに `LLAMAMAN_IDLE_TIMEOUT` を使用してください。
