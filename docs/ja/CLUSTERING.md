# クラスタリング

> **注:** これは翻訳であり、[英語版](../en/CLUSTERING.md)より内容が古い場合があります。英語版が正式な内容です。

*オプション機能、デフォルトは無効 — シングルノードのインストールには一切影響しません。*

複数の llamaMan デプロイメントが**1つの論理クラスタ**として機能します。単一のダッシュボードですべてのノードの GPU、インスタンス、ダウンロードを集約し、ノード間の起動/プル/ダウンロードや、複数ノードの共有キューによる負荷分散を実現します。ノード同士は共有ストレージバックエンドを介して互いを検出するため、ペアごとのキー交換は不要です。

**要件:**

- **共有ストレージバックエンド** - すべてのノードが**同一の** `DATABASE_URL`（MariaDB/MySQL、[Storage Backends](CONFIGURATION.md#storage-backends) を参照）を指定していること。JSON バックエンドはホスト単位であり共有できません。
- **ノードごとに一意の `LLAMAMAN_NODE_NAME`** - 各ノードのクラスタ識別子（すべてのインストールで設定必須）。
- **すべてのノードで同一の `CLUSTER_SECRET`** - ノード間のすべての HTTP 通信で使用される Bearer トークン（`X-Cluster-Secret` として送信）。
- **クロスノード*アクション*用の各ノードの `CLUSTER_ADVERTISE_URL`** - **他の**ホストからルーティング可能なホスト名/IP（`localhost` は不可、例: `http://srv1:5000`）。これが設定されていないノードはダッシュボードに表示されますが、表示専用（view-only）となります。

**各**ノードで設定（`LLAMAMAN_NODE_NAME` と `CLUSTER_ADVERTISE_URL` のみが異なります）:

```yaml
environment:
  - LLAMAMAN_NODE_NAME=srv1                 # unique per node
  - DATABASE_URL=mysql+pymysql://llamaman:pass@db-host:3306/llamaman   # identical
  - CLUSTER_ENABLED=true
  - CLUSTER_SECRET=a-long-shared-random-secret   # identical
  - CLUSTER_ADVERTISE_URL=http://srv1:5000  # this node's address, routable from peers
```

各ノードは約 5 秒ごとにハートビートを送信します。`CLUSTER_NODE_ONLINE_WINDOW_S`（デフォルト 45 秒）を超えて応答がないノードはオフラインとして表示されます。**Settings → Cluster** で確認および管理できます。

ホスト固有であるため、一部の設定はノード単位でスコープされます。追跡対象の **Docker images**、モデル上限エビクションのトグル、および[負荷時のウェイク設定](#waking-under-load)です。それ以外のすべてはクラスタ全体で共有されます。アクティブな共有キューグループのエイリアスは、選択可能なモデルとして `/api/tags` および `/v1/models` で通知（クラスタ全体で重複排除）されるため、クライアントがエイリアスを送信すると、それを提供している最も負荷の低いノードへルーティングされます。

**グループのコンテキスト長はクラスタ全体で統一されます。** クライアントがどのノードに問い合わせても、`/api/show` および `/v1/models` はキューグループのコンテキストを**トラフィックを受信できるノード上のすべてのアクティブメンバーの最小値（min）**としてレポートします。オフラインまたは表示専用のノード上のメンバーはカウントされません。異なる ctx 値のメンバーを持つグループは小さい方の値を通知するため、そのサイズに合わせたプロンプトはどのディスパッチ先でも安全です — 大きいメンバーの追加の余白は単に使用されません。グループのローカルメンバーを持たないノードでも応答します（`context_length` は共有インスタンス状態のピアのランタイム ctx、または共有 DB のプリセット行から設定されます）。どこにもアクティブなメンバーが存在しないグループは 404 / エントリなしを返します。このメンバーの ctx が通知された最小値を超えている場合、オペレーター UI のインスタンスカードには `ctx <min>, capped by <node/model>` と表示され、どのピアがグループのコンテキストを引き下げているかを確認できます。

> **セキュリティ:** クラスタシークレットにより、任意のピアがこのノード上でアクションを実行できるようになります。ノード間トラフィックは、信頼できるネットワーク上または TLS の背後で実行してください。

クラスタ関連の環境変数: [Clustering variables](CONFIGURATION.md#clustering)。

<a id="queue-groups"></a>
## キューグループ

キューグループは、1つの **Queue group name** の下にインスタンスをまとめ、クライアントがその名前を任意のノードに送信できるようにします。この表は、別のノードから見た各メンバーの扱いを示します:

| メンバーの状態 | `/api/tags` と `/v1/models` への掲載 | ルーティングされるトラフィック |
|---|---|---|
| 正常（healthy） | はい | 最優先 |
| 起動中（ロード中） | はい | 正常なメンバーの次 |
| スリープ中 | はい | 最後。フォールバックを含む起動中のすべてのメンバーの後。リクエストによってウェイクします。 |
| 停止処理中または停止済み | いいえ | なし |
| `CLUSTER_ADVERTISE_URL` のないノード上（表示専用） | いいえ | なし |
| オフラインのノード上（45秒間ハートビートなし） | いいえ | なし |

**ルーティングされた処理を受信するには `CLUSTER_ADVERTISE_URL` が必要です。** これがなくてもノードはピアにリクエストを送信できますが、どのピアもそのノードに到達できません。

**ここではスリープと停止は別のものです。** アイドルタイムアウトはインスタンスをスリープさせ、スリープ中のメンバーはトラフィックが必要とするとウェイクします。停止したメンバーは停止したままです: オペレーターによる停止、エビクション、クラッシュはいずれもこの状態になり、他のノードからのリクエストで再起動されることはありません。そのメンバーを保持するノードに問い合わせると `503` が返されますが、その名前がメンバー自身のファイルでもある場合は、引き続きウェイクします。

<a id="waking-under-load"></a>
### 負荷時のウェイク

起動中のメンバーはリクエストを拒否せずキューに入れるため、トラフィックだけではキュー全体があふれるまでスリープ中のメンバーに届きません。そこで llamaMan は1つのメンバーを先行してウェイクします。グループ内の正常なメンバーがすべて満杯で、リクエストがキューに入っており、ロード中のものがない状態が 3 回のポーリング（約 15 秒）連続すると、スリープ中のメンバーが1つウェイクします。クラスタ全体で、これを行うのはスリープ中のメンバーを保持するノードのうち名前が最も小さいノードのみで、1回のポーリングにつきグループあたり最大1メンバーです。プライマリはフォールバックより先にウェイクします。

対象となるのは、容量を増やせるスリープ中のメンバーのみです: **Max Concurrent** が `0` より大きく、同じノード上の起動中のメンバーとキューを共有していない必要があります。

モデルの重みがノードの空き VRAM に収まらない場合、ウェイクはスキップされ、ログに1行記録されます。このチェックはすべての GPU の空きメモリを合計し、重みのみをカウントするため、チェックに通ったモデルでもロードに失敗する可能性があります。VRAM を読み取れない場合、またはモデルに測定対象のファイルがない場合（Strata の仮想モデル）、ウェイクは実行されます。

どちらの設定もノード単位で、`POST /api/settings` から設定します:

| 設定 | デフォルト | 意味 |
|---|---|---|
| `eager_wake_enabled` | `true` | 負荷時にこのノードがスリープ中のメンバーをウェイクするかどうか |
| `eager_wake_polls` | `3` | ウェイクするまでの連続した飽和ポーリング回数（各 5 秒） |

<a id="when-a-group-cant-be-served"></a>
### グループを処理できない場合

他のノードがグループをホストしていても、どのノードもリクエストを受け付けられない場合、クライアントには "model not found" ではなく、各ノードとその理由を示すエラーが返されます:

| ステータス | コード（OpenAI ルート） | 意味 |
|---|---|---|
| `429` | `group_full` | 少なくとも1つのピアのキューが満杯です。再試行すれば成功する可能性があります。 |
| `503` | `group_unavailable` | ピアがオフライン、表示専用、到達不能、または準備未完了です。 |

所有ノードは自身のメンバーについて次の `503` コードを返し、エントリノードはこれを受け取ると次のメンバーを試します:

| コード | 意味 |
|---|---|
| `model_stopping` | メンバーがシャットダウン中です |
| `group_stopped` | このノード上のメンバーがすべて停止しています |
| `wake_failed` | ウェイクに失敗しました |
| `wake_timeout` | メンバーが時間内に正常な状態になりませんでした |

グループ名が、その名前を部分的に含むだけのローカルファイルを起動することはありません。名前が完全に一致するファイルは引き続き実行されます。

<a id="troubleshooting-a-group-that-isnt-visible"></a>
### 表示されないグループのトラブルシューティング

- **JSON バックエンドには共有された1つの `DATA_DIR` が必要です。** ノードはレジストリを通じて互いを見つけるため、ディレクトリが別々だと各ノードからピアが見えません。ディレクトリを実際に共有する場合を除き、MariaDB を使用してください。
- **劣化したデータベースは意図的にピアを隠します。** DB ミラーが読み取りを処理している間、ノードには自分自身しか見えず、ローカルで処理します。
- **ロードプローブの失敗でグループは隠れません。** 応答しないピアはスナップショット（最大 45 秒前）に基づいてルーティング可能なままですが、応答したすべてのピアより順位が下がります。ピアへのプローブが失敗し始めたときと回復したときはログに記録されます。
