## [1.6.2-1] - 2026-08-10

### Fixed
- **The local database mirror still could not be switched on from the UI.** 1.6.2 fixed a genuine defect on that path, but not the one operators were hitting, so the symptom was unchanged: the checkbox unticked itself a few seconds after being ticked, `DATA_DIR/db_mirror/` never grew past the `owner.json` marker written at startup, and nothing appeared in the app log or the browser console. The toggle had no change listener. Every other control in App settings registers `addEventListener('change', saveAppSettings)`, and `saveAppSettings()` did read `s-db-mirror-enabled` into its payload — but nothing ever called it when that checkbox changed, so ticking the box issued **no request at all**. `loadStorageStatus()` then reset the box from the effective state on its next poll, which looks identical to a save being rejected. Nothing was ever persisted, which is also why restarting the container did not help, and why `GET /api/storage-status` reported `last_sync_at: null` — not a failed sync, but no attempt ever made.
  - **`LLAMAMAN_DB_MIRROR=1` was the only way to turn the mirror on in 1.6.1 and 1.6.2.** The env var is read directly by `resolve_enabled()` at startup and never went through the UI path.
  - 1.6.2's `merge_settings` fix remains necessary: with the listener restored but that fix absent, ticking the box would persist the setting to the database and leave it inert until the next restart. Two independent defects sat on the same path, so neither fix alone made the feature work — which is why 1.6.2 changed nothing observable.

## [1.6.2] - 2026-08-10

### Fixed
- **The local database mirror could not be switched on from the UI.** Ticking **Settings → App settings → "Keep a local mirror of the database"** appeared to do nothing: a few seconds later the checkbox silently unticked itself, and `DATA_DIR/db_mirror/` contained exactly one file — the `owner.json` ownership marker written at startup — with nothing in the app log or the browser console to explain either. The setting *was* reaching the database; what never happened was the wrapper noticing. `ResilientBackend.merge_settings` short-circuited straight to the bare primary whenever mirroring was off, returning before the `resolve_enabled()` that re-reads the toggle — so the one write whose entire purpose is to flip the wrapper from off to on was the one write that could not observe itself. Runtime state stayed off, and because the UI deliberately drives that checkbox from the *effective* state reported by `GET /api/storage-status` (so that pinning via `LLAMAMAN_DB_MIRROR` shows honestly rather than as an unchecked box next to an active mirror), the next poll dutifully unticked it. The empty directory has the same single cause: `resolve_enabled()` is also what kicks the initial full pull, so with it skipped the mirror was never seeded and write-through never began. Pass-through now re-resolves the toggle on every settings merge. Turning the mirror **off** was never affected — that path runs while already enabled, so it took the full branch and resolved normally. **Affects 1.6.1 only.** On that build the mirror can still be enabled either by setting `LLAMAMAN_DB_MIRROR=1`, or by ticking the box and restarting the container, since startup re-reads the persisted setting and seeds from it. Covered by three regression tests; `tests/test_db_mirror.py` is now 53.

### Changed
- **The no-GPU banner said the wrong thing to most of the people who saw it.** It appears whenever `/api/gpu-info` returns an empty list, and that covers two very different situations: the host genuinely has no GPU, or it has one that llamaman cannot *read* — no `/sys/class/drm:ro` mount on AMD/Intel, no NVIDIA Container Toolkit `utility` capability, or a snapshot taken before any llama-server container exists to fall back to. The old copy asserted the first ("No GPU detected") and prescribed the remedy for it ("Set GPU Layers to 0 to run fully on CPU"), which is precisely backwards in the second case: monitoring access and *compute* access are separate grants, and a node whose GPU llamaman cannot see still attaches that GPU to every llama-server container it spawns. The banner was therefore telling operators of perfectly working GPU deployments to move them onto the CPU. It now names both possibilities, points at the mount and the capability that fix the readable-but-invisible case, and states plainly that a GPU llamaman cannot read still works for inference — before offering CPU-only as the answer for a host that really has none. Unchanged: the muted per-node "No GPU detected" line on cluster node cards, which reports a peer's empty GPU list and prescribes nothing.

## [1.6.1] - 2026-08-10

### Added
- **Surviving a database outage: an optional local mirror.** *(off by default)* With `DATABASE_URL` set, MariaDB is on the critical path of **every** request, not just of persistence — `api/auth.py` reads settings and verifies API keys on each call — so an outage doesn't degrade llamaman, it stops it: 500s on every route, no inference, no UI. And because `MariaDBBackend.__init__` runs `create_all()`, an outage spanning a container restart means the worker never boots at all. Turn on **Settings → App settings → "Keep a local mirror of the database"** (or set `LLAMAMAN_DB_MIRROR=1`) and the node keeps a write-through copy in `DATA_DIR/db_mirror/`, then keeps working from it when the database goes away: inference on both ports, launching and stopping models, downloads and hashing, and creating or editing presets, API keys, settings and Hugging Face tokens. Offline changes are replayed in order on reconnect. With the toggle off the wrapper does zero mirror I/O and behaves byte-identically to the bare backend.
  - **The breaker is all-or-nothing** — three consecutive connection-class errors, then an atomic switch to mirror/journal mode. Below that, exceptions propagate exactly as they do today; falling back earlier would interleave journalled and applied writes and let an older replayed delta silently revert a newer one. `IntegrityError`/`ProgrammingError` are never counted as an outage — they are bugs, and `merge_settings` depends on catching `IntegrityError` itself. Once open, reads don't touch the database at all: otherwise every request pays a TCP connect timeout, which is the difference between an app that feels degraded and one that feels hung.
  - **Offline writes are classified, not uniform.** Node-scoped rows (instance/download state, `model_files`, the cluster heartbeat) go to the mirror and reconcile wholesale on reconnect, since this node is their only writer. Shared rows — presets, API keys, settings — are journalled and replayed as the **edit** rather than the resulting row, so a change another node made during the outage survives: a different preset, a different field of the same preset, a different settings key or Hugging Face token are all left intact. The journal entry is `fsync`ed *before* the mirror write, so a change that cannot be recorded is refused rather than accepted and lost, and every op is idempotent so replay-from-the-top after a crash is safe.
  - **Blocked while offline:** first-user `/setup`, and the full-blob `save_settings` that would stomp every key a peer changed during the outage. Both surface as **503** through a single errorhandler, so no route needs to know the backend can be degraded. Request-log records are **dropped, not buffered** — they carry full request *and* response bodies, and spooling them through a long outage could fill the volume and take down the inference this exists to protect.
  - **Recovery** probes every 10s, runs pending migrations against the real database (through the wrapper, the recorded schema version would come from the mirror and can be ahead of what this node applied), replays the journal, and only then closes the breaker — so no request observes a half-replayed state. Migrations never run degraded; startup skips them and defers to this path.
  - **Cluster peers are deliberately not mirrored.** `register_node` stamps a local-clock heartbeat, so mirrored peer rows would republish every node as freshly alive and let the dispatcher forward inference to nodes we have no coordination store for. A degraded node sees only itself and serves locally, which is the honest answer; peers likewise stop routing to it.
  - Each node needs **its own `DATA_DIR`** — the mirror directory is stamped with its owning node id and switches itself off rather than let two nodes interleave their rows. A daily full pull picks up rows written by *other* nodes, which write-through cannot see, and turning the mirror **off** during an outage is deferred to recovery, since pass-through against a database already known to be unreachable would raise on every read. New **`GET /api/storage-status`** and a dashboard banner report how long the database has been down and how many changes are pending. Covered by 50 new tests in `tests/test_db_mirror.py`.
- **`LLAMAMAN_DB_MIRROR` env var.** Forces the local mirror on (`1`) or off (`0`), overriding the per-node setting; only meaningful with `DATABASE_URL`. The UI drives its checkbox from the *effective* state and disables it when pinned, so an operator doesn't see an unchecked box next to a banner saying the mirror is active.

### Fixed
- **Settings writes could silently drop another node's concurrent change.** Adding or removing a Hugging Face token, and removing a model's recorded source, all did `get_settings()` → mutate → `save_settings()`. Settings are **one** shared row, so anything another writer changed between that read and that write was rewritten away — and on a shared database, "another writer" means any other node in the cluster. Two new backend primitives now do the read-modify-write inside the backend's own lock (`SELECT … FOR UPDATE` on MariaDB): **`edit_settings_list`** for list-valued keys of `{"id": …}` entries, which records the addition/removal rather than the resulting list so two nodes adding tokens concurrently cannot drop each other's, and **`replace_settings_key`** to set exactly one key outright — something `merge_settings` cannot express, because it deep-merges and so can never *remove* an entry from a dict-valued key. Pre-existing; the window was small online but is the entire length of an outage once the mirror is in play.

### Changed
- **`StorageBackend` gained two abstract methods** (`edit_settings_list`, `replace_settings_key`); both built-in backends share one helper so their semantics can't drift, and a custom backend subclass will need them before it can be instantiated. **Upgrade note:** no schema change and no migration — the mirror is off until you turn it on, and JSON-backend installs are unaffected by everything above. Before enabling it, note that secrets are mirrored to local disk: settings are copied verbatim, so Hugging Face tokens land in `DATA_DIR/db_mirror/settings.json` in **plaintext**, and an API key **revoked** offline stays valid on other nodes until the database is back.

## [1.6.0] - 2026-08-03

### Added
- **Tab-title notification when a model finishes loading.** Loading a model is the one long, unpredictable wait in the UI, and it is spent in another tab. When an instance reaches `healthy` while the dashboard tab is hidden, the title becomes `● llamaMan` (`●2`, `●3`, … for several at once) and clears the moment you look at the page again. No setting, no asset, no permission prompt, and the model name is deliberately omitted because browsers truncate tab titles hard once several tabs are open. Two things qualify as "became ready": an instance watched flipping from non-healthy to healthy, and one that first appears already healthy but started less than 300s ago. The second rule exists because a peer's instances arrive through its heartbeat snapshot (5-15s behind) and browsers throttle timers in hidden tabs, so for a remote launch the `starting` phase is frequently never observed at all; the freshness bound is what stops a peer returning from offline announcing its long-running models. Instances already running when the page loads never announce.

### Fixed
- **The dashboard stopped loading anything until a page refresh.** A model's **Logs** or **Stats** button, or the Logging page, could sit on "Loading…" forever while the rest of the page silently stopped updating, and only F5 recovered it. The cause was the dashboard polling every peer that was **online** — which only means "wrote a heartbeat row into the shared database within the last 45s" — instead of every peer that was **reachable**, the HTTP probe the server already runs and ships on the same payload. A node can do the first while being unreachable over HTTP from here (a peer behind a VPN tunnel or a NAT with no return path is the common case), so those calls hung. Each one held one of the browser's ~6 connections per origin, and at one round every ~9s against a 60s timeout they accumulated past that cap, after which every later fetch on the page queued and was never dispatched — no error, no timeout, nothing for a `catch` to report, which is why it presented as an eternal spinner rather than a failure. The peer fan-out now requires `online && reachable`. **Note:** reachability is cached for 15s, so a peer that has just recovered may take that long before its resource bars repopulate.
- **Node-to-node calls waited as long for a dead peer as for a working one.** `requests` reads a scalar `timeout` as *both* the connect budget and the read budget, so every peer call silently inherited a connect timeout sized for the slowest legitimate response — up to five minutes on the inference path, each one pinning a gunicorn thread. The cluster control proxy goes from `timeout=60` to `(3, 60)`, cross-node inference forwarding from `REQUEST_TIMEOUT` to `(5, REQUEST_TIMEOUT)`, and `cluster_request()`'s own default is now `(3, 10)`. Connecting is only a TCP handshake against a listener that is up regardless of what it is doing, so it deserves a far tighter bound than the response does. Failover semantics are unchanged: a `ConnectTimeout` is not a `ReadTimeout`, so it still falls through to "the peer never accepted this, try another node", while a genuine read-timeout still returns the 504 that stops the same prompt being processed twice. **Upgrade note:** raising `REQUEST_TIMEOUT` no longer extends how long a node waits for a peer to *answer the door* — that is pinned at 5s — only how long it waits for the response once connected. The read budget still covers on-demand model loading plus time to first token, unchanged.
- **Browser pollers had no deadline.** A `fetch()` with no `signal` waits essentially forever, so any poller that re-fires faster than its requests complete accumulates stuck requests until the page's connection budget is exhausted — the amplifier behind the bug above, and a hazard independent of it. Every polled endpoint now aborts itself (10s, or 15s for `/api/cluster/nodes`, which probes peers inline). Deliberately not applied to user-initiated actions: image pulls, launches and restores are still allowed to take as long as they need. **Requires** a browser with `AbortSignal.timeout()` — Chrome 103+, Firefox 100+, Safari 16+.

### Changed
- **Background tabs no longer poll peer nodes.** The cross-node container-stats fan-out is skipped entirely while the dashboard tab is hidden, so a dashboard left open in a background tab stops asking peers to run `docker stats` for nobody. Existing stats are kept rather than cleared, so remote resource bars do not blink out when you return.

## [1.5.5] - 2026-07-23

### Added
- **Per-model Display Name.** (#64, #65) An optional friendly name, set on the Launch form's `Model Path | Display Name | Note` row, that is advertised as the model id on `/api/tags` and `/v1/models` and accepted as an inbound model name - so OpenWebUI shows `Qwen 2.5 14B` instead of `Qwen2.5-14B-Instruct-Q4_K_M`. Stored on the preset (no migration). It is translated to the canonical file stem once at the request boundary, so everything downstream (`share_queue_group`, `dispatch_inference`, the request gate, work-stealing) only ever sees file stems - cluster aliasing is untouched. Uniqueness is enforced: duplicates, a name shadowing another model's filename, a clash with a queue group, `:`, or >100 chars are rejected.
- **Detect and re-pull republished models.** (#66) Authors routinely republish a repo under the same filenames (a requant, a fixed chat template, a rebuilt imatrix), so a model pulled months ago can be silently stale. **Check for updates** compares the local file against HuggingFace's published content hash in one HTTP request with no download; an armed **update available** re-pulls into a staging folder nested inside the model's own directory and atomically swaps each file in only once the download completes. It is an ordinary download record, so speed limits, tokens, progress, pause/resume/cancel and auto-retry all apply, and multi-shard models work automatically. It refuses with **409** while an instance has the model loaded, and never touches the live file until a complete download exists.
- **Verify a model by hashing it locally.** (#67) For models with no recorded hash, hashing the bytes already on disk settles "did this change?" with no network, on a worker thread with progress, and records the result so it is a one-time cost. `POST /api/models/verify-hash` starts (or rejoins) a job; `GET` reports only.
- **Background update-check worker.** (#68) Opt-in under **Settings >> Download Settings** (`auto_update_scan_enabled`, default off; `auto_update_scan_interval_hours`, default 24). Runs on its own thread, skips entirely while a download is running, and hashes at most one model per pass, so by the time you click the answer is exact and instant.
- **Advertise cluster queue-group names in the model-listing APIs.** (#81) Each live `share_queue_group` alias is surfaced as a model entry in `/api/tags` and `/v1/models` - deduped cluster-wide - so a client can discover the load-balanced name it should send. Only when clustering is on, the alias is set, and a non-stopped member exists on any node. Name collisions with a file or Display Name are skipped.
- **`SESSION_COOKIE_NAME` env var** (default `llamaman_session`). (#63) See below.

### Fixed
- **Session cookie collided with other Flask apps on the same host.** (#63) Cookies are scoped by host+path, not port, so a second Flask app using Flask's default `session` cookie name clobbered ours (and vice versa), logging users out of one app when they logged into the other. Now namespaced via `SESSION_COOKIE_NAME`. **Upgrade note:** every existing session is invalidated once on deploy - users simply log in again.
- **`list_repo_files` never requested `?blobs=true`.** (#69) The HF model API returns `rfilename` only unless `?blobs=true` is passed, so file sizes came back `None` and there was no content hash to compare against. Pre-existing.
- **HF content hash silently lost by following the redirect.** (#70) `x-linked-etag` (the blob sha256) lives on HuggingFace's 302, not the CDN response it points to, so `allow_redirects=True` lost it - and the CDN's own `etag` is a different 64-hex value that would report every model changed forever. Now `allow_redirects=False`, trusting only `x-linked-etag`. Regression-tested.
- **Display Name could be captured by a cluster queue group.** (#71) The `share_queue_group` shortcut matched by substring and ran before model lookup, so a display name `"qwen"` was captured by an unrelated group `"qwen2.5-14b"`. An exact display-name match now takes precedence.
- **Saving the launch form wiped the Display Name.** (#72) The full preset `PUT` rebuilt the preset from scratch and carried over only `favorite`/`note`; it now carries the display name too.
- **Update button rendered with no model selected or no known repo.** (#73) An explicit `display` rule beat the `hidden` attribute; fixed with `.settings-tab-update[hidden] { display: none }`.
- **Hash progress bled across model selection.** (#74) Button state is now keyed by node + path and `renderUpdateButton()` is the only DOM writer, so a response for a model you navigated away from can't leak onto the one you're viewing; selecting a model rejoins any running job.
- **`GET /api/models/verify-hash` started a hash instead of reporting.** (#75) Merely selecting a model (or a peer asking about one) could kick off a multi-minute full-disk read. POST starts, GET reports.
- **Update/verify always hit the local node in a cluster.** (#76) Checking a model on a remote node failed with "model file does not exist"; update-check, verify-hash and re-pull now route to the owning node via the existing cluster proxy.
- **Deleting a model while it is being hashed.** (#77) The delete endpoint now refuses with **409** while a hash is in flight (mirroring the loaded-model refusal), and the UI checks too.
- **`merge_settings` had no lock in the MariaDB backend.** (#78) The unlocked read-modify-write of the single shared settings row let two writers lose each other's keys. Now `SELECT ... FOR UPDATE` for the merge; `save_settings` locks too; the row-absent case retries once. Pre-existing.
- **Cluster-wide `schema_version` made per-node migrations silently skip.** (#79) `schema_version` lived in the global settings blob, so on a shared database one node's migration bumped it and later nodes skipped their own per-node work. The schema version is now tracked per node; existing installs inherit the old global number, capped so only global-only migrations count as done.

### Changed
- **Per-node model metadata store.** (#80) A model's source repo and content hash describe bytes on one node's disk, but lived in the global settings blob keyed by path, so two nodes at the same path collided. They now live in a node-scoped `model_files` table keyed `(node_id, model_path)`, created on each node's boot; migration 004 adopts only paths that exist on that node's disk, and the legacy blob is kept as a read fallback and rollback path (never destructively touched). **Deploy note (MariaDB):** the composite key is 3056 of InnoDB's 3072 index bytes under utf8mb4, so the table uses `ROW_FORMAT=DYNAMIC`.

## [1.3.4] - 2026-07-16

### Added
- **Speculative decoding: MTP can now draft from a separate drafter model.** The launch form's **Draft Model** field, previously shown only for DFlash, is now offered for `draft-mtp` as well and passes the drafter to llama-server as `--model-draft`. This is what the standalone MTP-head GGUFs published alongside main-model weights need — e.g. a Gemma 4 assistant-MTP drafter running in front of a QAT main model — a pairing llamaman previously had no way to launch except through Extra Args. Leave the field blank and nothing changes: no `-md` is sent, and llama-server drafts from the MTP heads built into the main model.
  - **Draft Model** is now visible whenever Speculative Decoding is on, its label marking it `(optional)` for MTP and `(required)` for DFlash as you switch **Draft Type**. It still suggests the GGUFs present on the target node while accepting a hand-typed path under the models directory, and the drafter is reached inside the spawned container through the existing read-only models mount.
  - Validation is unchanged: only DFlash rejects a blank drafter — at the form, and with a **400** from `POST /api/instances` / `PUT /api/presets` for callers that bypass the UI. MTP accepts either.
  - No new preset keys. The existing `spec_draft_model` simply applies to both draft types now, so it flows through launch, restart/relaunch, preset save/load, the preset-merge used by Ollama/OpenAI auto-launch, and state restore exactly as it already did.
  - Whether any given model's MTP drafter actually loads is up to the llama.cpp image you run (`LLAMA_IMAGE`); llamaman's job here is passing the flags through. Gemma 4's MTP support in particular was still on a llama.cpp PR branch at the time of writing.
  - **Upgrade note:** MTP previously ignored a drafter path left over in a preset from a DFlash config; that path is now honored and sent as `-md`. If you configured DFlash with a drafter, switched **Draft Type** back to MTP, and saved, clear the **Draft Model** field before your next launch — otherwise llama-server receives a DFlash drafter under `--spec-type draft-mtp` and fails to start. Presets that never set a drafter are unaffected, and the field being visible under MTP now makes any such leftover value visible rather than silently ignored.
